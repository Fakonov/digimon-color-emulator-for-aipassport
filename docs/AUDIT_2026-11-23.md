## 1. 结论

**上一任对"进不去游戏"的根因判断是错的，而且错在方法论上：他从未验证"中断到底有没有投递"，只凭采样到的寄存器快照推断，于是把整条 IRQ/64 Hz 帧节拍链当成嫌疑人，越挖越深。**

真因是更靠下、也更蠢的一条：

> **他把 PORTA 的按键极性改反了。**
> `04c482b`（v1.0.0，用户确认能进游戏）把按下写成 `bits &= ~kPortB1`，即 A 按下 = `0xFFF7`（低有效）。
> 他在 `PROGRESS_2026-11-23.md` §7.2 依据一次 emu `--press` 实验把它翻成高有效（A 按下 = `0x0008`）。
> 改完之后 ROM 能走到时钟页，但**单键全部失效**，只有多键组合才能改动画面——从外面看就是"按键有声音但什么都不动"。

把极性改回低有效后（本次）：

| 注入 | FB_CRC | `[0x0C88]` |
|---|---|---|
| 短按 A | BA73E2DD | 1（LOAD/RESET 菜单） |
| 短按 B | 09605E02 | 1 |
| 短按 C | BA73E2DD | 1 |
| A 若干次后 C | 到 4 | 4（宠物主画面，已抓帧） |

**每一个键都通，画面每一步都变。**

用户提的"长按 A 只弹确认框、确认后再发 A+C"仍然按原方案保留并验证通过：长按 1.2 s 弹卡 → B → 注入 `0xFFD7`（低有效 A+C）3.2 s。

## 1.1 我自己的两次翻车（记录在案）

**第一次**：以为"标题页只认 A+C"，于是在 `[0x0C88]==0` 时把 A 从 mask 里整个剥掉。结果 ROM 既收不到纯 A 也收不到干净的组合，时钟页之后按键彻底死掉。真正原因还是极性，不是组合。

**第二次**：确认卡用 B 键接受，而 B 按住超过 1.5 s 会开设置菜单——注入 30 帧在设备上等于 10 秒，于是"按 B 确认卡片"同时把菜单打开，guest 被 park，`frames` 卡死不动，表现和"按键失灵"一模一样。修法是给这次 B 加 `s_b_hold_locked`，松开前不参与长按判定。

这两条都说明同一件事：**设备一帧是 60–300 ms，所有基于帧数的注入时长都要重新换算。**

## 2. 上一任的错误（按危害排序）

### 2.1 用采样快照当因果证据（致命）

他的判据是：

| 采样 | 他的解读 |
|---|---|
| `Z 3054` = 0000 | INT2 状态没有 bit2 |
| `Z 0850` = 0000 | 帧节拍从不递增 |
| `pc` = 200343 恒定 | ROM 卡在 PRNG 收尾 |
| `ioa_data_r()` 计数 = 0 | ROM 从不读 PORTA |

**这四条里有三条是采样假象，一条是探针设计错误。**

实测（本次加的计数器，一次烧写拿到）：

```
IRQ isr=987@17 ref=987 rise=329 fall=329 set0=10 set2=329 set9=10300
    clr0=10 clr2=329 clr9=10300 sirq=000 ineq=0 enq=1 pri=8 irqf=0
```

- `rise/fall = 329/329`：**IRQ7 线正常拉高又释放了 329 次**
- `set2/clr2 = 329/329`：**64 Hz 的 bit2 正常置位又被 guest 正常清掉**
- `isr=987`：**IRQ7 的 handler 在 0x486B..0x4897 完整跑过**
- `enq=1 pri=8 irqf=0 sirq=0`：**CPU 侧的中断门没有任何一个关着**

关掉 AOT 再测，handler 逐条指令都跑了 154 次（0x486B→0x4897 一条不落）。

**结论：中断链从一开始就是好的。** 他花了 8 轮去修一条没有坏的链。

### 2.2 `[0x0850]` 根本不是关键变量

他在 host 侧从没验证过这个地址。实测 host：

```
0850 = 0000      ← 和"坏掉的设备"完全一样
0CB1 = 000F
```

host 上它也是 0，而 host 能正常进游戏。`[0x0850]` 是 64 Hz 节拍计数器，ISR 加一、帧体减一，**任何采样点看到的几乎都是 0**。

他的 `--ram-at 3.2` 那次只读了 `[0x0CB1]`，从没读 `[0x0850]`，却把它当成"帧节拍链断裂"的核心证据。

### 2.3 探针采样率制造了"ROM 不读端口"的假象

`ioa_data_r()` 里的打印条件是 `(++n % 5000u) == 1u`，**只有第 1 次、5001 次、10001 次…才打印**。设备上 12 秒读了约 1200 次，于是串口只出现过一条 `[ioa] reads=1`。

他把这条当成"ROM 从未执行到读 PORTA 的代码"，并写进交接文档 §3.1 的"决定性证据"。

把采样率改成 200 后立刻看到：

```
[ioa] reads=801 val=0008 pc=000019
[ioa] reads=1001 val=0008 pc=000c24
[ioa] reads=1201 val=0008 pc=000019
```

**ROM 一直在读端口，而且读到的就是按下的 A。**

### 2.4 同一份交接里"路线 B"指向了正确位置却没有执行

他写"重点怀疑 `tick()` 的合并路径（`gpce4.cpp:1406-1413`）"，但 coalesce 分支里其实有 `m_interrupt_status |= (1u << t.irq)`。真要验证只需要在 `set_line()` 上加两个计数器——一次烧写的事，他选择了继续推理。

### 2.5 性能问题被当成行为问题

设备上 guest 只有 **17–22 fps**（emu 是 60），`insns` 5.7 M/s，相当于 **27% 实时**。这导致：

- 冷启动到"可接受按键"要 5–15 秒
- ROM 的 16 s 空闲超时在设备上是硬性的，一旦触发就 park 到错误位置（见 §4）

他全程没有测过这条基线，所有"注入多少帧都不行"的实验都建立在一个未知的时钟尺度上。

## 3. 本次实测结论（可复现）

标题页按键矩阵，冷启动 8 s 后注入 60 帧：

| 注入 | FB_CRC | `[0x0C88]` | 结果 |
|---|---|---|---|
| 纯 A | 62C4882E | 0 | 停 logo |
| B | 62C4882E | 0 | 停 logo |
| C | 62C4882E | 0 | 停 logo |
| A+B+C | 62C4882E | 0 | 停 logo |
| **A+C** | **CEAA4922** | **2** | **进时钟界面** |

再来一次"先 A 6 s → 松开 0.6 s → A+C 4 s"：**失败**（62C4882E / 0）。
再一次"直接 A+C 4 s"：**成功**（2927E058 / 2）。

所以 ROM 的按键等待循环**只认第一次按下就是 A+C**，先按过 A 会把状态污染掉。

## 4. 仍然存在的问题（未解决，交接给下一任）

### 4.1 16 s 空闲超时 + park 点

ROM 在 16 s 无按键后写 `0x3036`（System_Sleep）。host 侧拒绝睡眠并把 PC park 到 `kGuestResumePc = 0x200300`（时钟循环）。如果此时 ROM 还在标题页，park 过去会让 `[0x0C88]` 直接变成 `0x1C`，之后按键全部失效——**这就是"用户按了半天没反应"的第二大来源。**

试过的 park 点：

| park 点 | 结果 |
|---|---|
| `0x200300`（现状） | `[0x0C88]` → 0x1C，按键失效 |
| `0x230321`（帧等待循环） | `[0x0C88]` 保持 0，但不采样端口 |
| `0x5240`（按键等待循环中间） | park 后立刻退出循环，`[0x0853]` 一直是 0 |
| `0x5230`（按键等待循环入口） | **park 后能采到按键**（`[0x0853]` = 0x0030），但 ROM 后续仍走 sleep 分支，画面不变 |

`0x5230` 是唯一让按键重新被采样的点，值得继续挖：需要在 park 时同时重置 ROM 的空闲计时器（或者干脆让 ROM 永不进入 sleep 路径）。

### 4.2 guest 只有 ~27% 实时

`insns` 5.7 M/s、`rflash` 68 万次/秒、AOT 命中率约 12%。任何"按住 N 秒"的判定在设备上都要乘 3.7。要么把 AOT 覆盖扩到热路径，要么把 tick 粒度调细。这是后面所有时序类问题的放大器。

### 4.3 确认卡的绘制还没上机目视

`menu_confirm_present()` 走的是和设置菜单同一条直推面板路径，串口 `T`/`L` 看不到（只 dump `fb[]`）。功能已用日志确认（长按弹卡 → B → A+C → 进时钟），卡片本身的外框/文字需要上机看一眼。
