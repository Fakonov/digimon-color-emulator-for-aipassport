## 0. 结论先说（可执行的判断）

1. **切时钟界面不是「一帧瞬切」，是 4 个 guest 帧的逐带重绘。**
   实测：按键后第 4 帧开始，连续 **4 帧**（emu 帧 244-247）向 LCD 推了 **26,496 像素 = 2.87 个整屏**，
   画面上能看到 **3 个可分辨的中间状态**（旧画面下半 → 新画面+黑条 → 新画面）。
   guest 侧耗时 = 4 × 1.6 M = **6.40 M guest cycles = 66.7 ms guest 时间**。
   证据：`tmp/r6b/B/frames.csv` 帧 244-247 的 `lcd_px`；`tmp/r6b/clk1/fb_000244..247.bmp`。

2. **这 6.40 M guest cycles 的分配（实测 + 逐指令代价合成，见 3）：**

   | 区间 | guest cycles | 占比 |
   |---|---|---|
   | PRNG 忙等 `0x2002F4-0x200343` | 2,209,651 | **34.5 %** |
   | LCD 推送循环 `0x005B4A-0x005B8F` | 1,674,216 | **26.2 %** |
   | 键控 blit `0x207CA3-0x207CC6` | 1,154,486 | **18.0 %** |
   | 32x32 乘法 `0x005F8B-0x005FBF` | 415,584 | 6.5 % |
   | 绘图库其余 `0x207A00-0x207D00`（不含 blit） | 389,660 | 6.1 % |
   | 主循环 `0x230000-0x2303FF` | 222,625 | 3.5 % |
   | 时钟 idle `0x200340-0x20034F` | 212,760 | 3.3 % |
   | 常量填充 `0x005B1E-0x005B49` | 7,728 | **0.12 %** |
   | park `0x005000-0x0053FF` | 10,775 | 0.17 % |
   | 其余（page 0x207 / 0x004 等） | ~104,000 | 1.6 % |

   合计 6,401,881 cycles（4.00 帧），覆盖 1,332,428 / 1,479,243 条指令 = 90 %（口径见 8.3）。

3. **「大面积元素移动」的原语不是常量填充，是「blit 进 96 word 行缓冲 + 推送循环刷窗」。**
   常量填充循环在整次切换里只跑了 **143 个像素（0.12 %）**；44 % 的 guest cycles 花在
   「键控 blit → RAM 行缓冲」和「行缓冲 → LCD 窗口」这两条循环上。见 5。

4. **数据 cache 不是这次慢的主因，量级差了 70 倍。**
   整次切换从 flash 读的精灵数据只有 **9,240 word = 18.5 KB = 578 条 32 B cache 行**；
   按 DIO 约 300 周期/行算约 173 k host cycles 约 **1.1 ms**，占 4 帧 292 ms 的 **0.4 %**。
   R6 0.2.3 把「剩下的主体」归给数据读，这个结论在算术上不成立（见 5.3）。

5. **要「和原机一样快」，重绘场景的宿主成本必须 <= 1.67 host cycles / guest cycle。**
   现在 7.3，稳定态已经做到 1.4。也就是说：**目标不是「再快 4.4 倍」，而是让重绘路径追平稳定态**
   （1.4 时 guest 速度 114 M cycles/s，比 96 M 的原机还快 19 %）。见 6。

## 1. 方法与工具（含两个必须先知道的坑）

PC 侧模拟器 `emu/` 是逐指令对拍过 MAME 的参考实现（`docs/EMU.md`）。
本轮没有改任何 emu 源文件，写了一个独立探针 `tools/r6b/probe.cpp`：
链接 `emu/obj/{isa_amalgam,aot_blocks,gpce4,st7735,audio_dump}.o`（去掉 main.o），
用 `struct ProbeSoc : Gpce4` 重写 `write16` 观测 SPI2（0x3092）字节流，从 `soc.lcd` 模型状态重建
每次 CASET/RASET/RAMWR 窗口；用 `m_insn_hook/m_cycle_hook` 取每 PC 指令数与周期；帧边界自建。
构建：`tools/r6b/build.ps1`（w64devkit g++，与 emu 相同 flags）。

### 1.1 坑一：装 hook 会静默关掉 fast path（本轮最重要的方法学发现）

`emu/unsp_glue.cpp:1106`：

    if (m_insn_hook == nullptr && m_cycle_hook == nullptr)   // 无 hook 才走快路径
    ...
    while (...) { if (fast_hot) {...hot_block_prng...}  if (wait_loop_collapse(lpc)) continue; ...

`emu/unsp_glue.cpp:1212`（有 hook 的分支）里 **没有** `fast_hot` / `wait_loop_collapse` / `spin_collapse`，
全部退化成 AOT 块或解释器。后果不是「变慢」，而是**行为变了**：

- 同一场景（复位，第 400 帧按 B）两种跑法各 dump 4 KiB RAM：**只有 8 个字不同，全在 PRNG 状态 0x0600-0x0607**，
  其余 4,088 个字逐字相同（`tools/r6b/ramdiff.py` 输出「words differing: 16 of 4096」，其中 8 个是栈槽）。
- 但这 8 个字足以改变 UI 分支：`GPCE4_HOT=0` 时标题画面按 B **不再切屏**，`GPCE4_HOT=1` 才切。
  即 `hot_block_prng` 与「解释执行 0x2002F4..0x200342」在**周期计费上不等价**，每帧 PRNG 迭代次数不同
  → 相位漂移 → 分支不同。
- 因此：**任何带 `--pc-hist` / `--block-hist` / `--trace-cycles` 的跑法，都不能直接当作设备行为。**

### 1.2 坑二：AOT 块从不调用 cycle hook

`emu/aot.h:262` 定义了 `AOT_CYC(c,pc,n)`，但 `emu/aot_blocks.c` 里 **`AOT_CYC` 出现 0 次**
（块把每条指令的代价累进局部 `cyc`，退出时 `c->icount -= cyc` 一次性扣，见 `emu/aot_blocks.c:15564`）。
所以 `--trace-cycles` / cycle hook 只能看到「没被 AOT 覆盖」的那一小撮指令，逐 PC 周期账严重偏小。
我第一版就是因此得到「5 帧 86 k cycles」的假数。

**本轮采用的正确做法（两步合成）：**

1. **代价表**：`GPCE4_AOT=0`（纯解释器）+ cycle hook，取每个 PC 的 `cyc/insn` → `tmp/r6b/A/costs.txt`。
   逐指令代价是 ISA 模型的固有属性（每条指令 `m_icount -= n`），与跑法无关。
2. **计数表**：`GPCE4_AOT=1` + `GPCE4_HOT=0` + insn hook，取重绘 4 帧里每个 PC 执行了多少次 →
   `tmp/r6b/B/counts.txt`。这一步的像素数与参考跑法一致（26,496 vs 26,400，差 0.36 %，
   `tmp/r6b/B/wins.csv` vs `tmp/r6b/clk1/wins.csv`），说明它复现的是**同一个事务**。
3. 合成：`cycles[pc] = counts[pc] * cost[pc]`（`tools/r6b/compose2.py`）。
   结果覆盖 4.00 帧（6,401,881 cycles，理论 6.40 M），误差 0.03 % —— 这个合成本身就是自校验。

### 1.3 场景复现

按 `docs/HANDOFF_2026-11-23.md:186` 记录的序列（load `saves/flash.bin`，第 240 帧按 0x0008）进入时钟界面；
`--clock-sync` 在第 120 帧把本机时间写进 0x0CAF/0x0CAE/0x0CAD 并置 0x0CB0=1（`emu/main.cpp:441`）。

    .\tools\r6b\probe.exe --frames 260 --press "8:240:270" --load-flash saves\flash.bin ^
        --clock-sync --nohooks --csv tmp\r6b\clk1\frames.csv --windows tmp\r6b\clk1\wins.csv

## 2. Q1：切换动作的形状 —— 几次 blit、几次 push、瞬切还是逐帧

### 2.1 事实

| 指标 | 值 | 证据 |
|---|---|---|
| 参与重绘的 guest 帧 | **4 帧**（帧 244-247） | `tmp/r6b/clk1/frames.csv` |
| 每帧 LCD 推送像素 | 889 / 11,015 / 14,400 / 96 = **26,400** | 同上 `lcd_px` 列 |
| 整屏（9,216）当量 | **2.87 屏** | 26,400 / 9,216 |
| 编程过的窗口 | **2 个**：(0..95, 42..113)=96x72、(0..95, 90..113)=96x24 | `tmp/r6b/clk1/wins.csv` |
| 通过 96x72 窗口推的像素 | 24,096 = **3.49 x 窗口面积** | 同上 |
| RAM 侧 blit 像素（0x207CA3 迭代） | **9,240** | `tmp/r6b/B/blits.csv` |
| 常量填充像素 | 约 143（7,728 cycles / 54） | 3 |

关键：**没有任何一次「整屏 96x96 窗口」的全屏 push**。整屏 push 只在上电 logo 出现过一次
（帧 14：窗口 (0..95, 18..113)，9,216 像素一次推完，`tmp/r6b/C/wins.csv:2`）。

### 2.2 是瞬切还是动画

- 逐帧看画面（`tmp/r6b/clk1/fb_00023x.bmp`）：帧 244 时**上半屏已是新画面、下半屏还是旧 logo**；
  帧 245 新画面 + 一条未绘制的黑竖条；帧 246/247 黑条收窄消失 → **可分辨的中间态 3 个**，
  跨 4 帧 = 66.7 ms guest 时间。
- 判定：**不是瞬切，是「按带重绘」的 4 帧过渡**；但也不是滚动/擦除动画（guest 没有逐帧平移源数据，
  而是每帧重画不同窗口区域）。用户说的「画面移动慢」= 这 4 帧被拉长到 4 x 73 ms 约 292 ms。
- **推测**：ROM 的意图是「先画 72 行带（3.5 遍：底图/精灵/文字），再补 24 行带」，
  因为 24,096 恰好 = 3.5 x 6,912（96x72），2,304 恰好 = 1 x 96x24。此解释只有算术巧合支持，没有调用栈证据。

### 2.3 「几次全屏 blit」

- 按**整屏（9,216 px）当量**：blit 9,240 px 约 **1.0 屏**，push 26,400 px 约 **2.87 屏**。
- 按**调用次数**：0x207CA3 不是「一次整屏调用」，它每像素迭代一次；4 帧内共 9,240 次，
  期间源指针不连续跳变 133 次（`runs` 列 30+63+40+0）—— 即约 **133 段**很短的行段/小矩形
  （目标恒落在 0x07BA-0x081A 的 97 个 word 内，见 5.1）。

## 3. Q2：guest cycles 分解与「139 cycle/像素」验算

### 3.1 合成结果（4 帧合计 6,401,881 cycles）

见 0 的表。要点重排：

- **推送循环 26.15 %**（0x005B4A-0x005B8F，371,496 条指令，CPI 4.51）：1,674,216 / 26,496 像素 =
  **63.2 cycles/像素**，与任务书的 63 完全一致。
- **blit 循环 18.03 %**（0x207CA3-0x207CC6，249,552 条指令，CPI 4.63）：1,154,486 / 9,240 像素 =
  **124.9 cycles/像素**。
- 两者相加 = 2,828,702 cycles = **44.2 %**，是「重绘」的真身。
- 绘图库 0x207A00-0x207D00 合计（blit + 其余）= 1,544,146 = **24.1 %**。
- 乘法 0x005F8B 6.49 %；65,416 条指令 / 9,240 像素 约 7 条/像素 → **推测**是每行段一次
  「段内偏移 x 2 字节」与「源地址 + y x stride」的 32x32 乘法。
- **PRNG 忙等 34.5 %**：重绘期间 guest 仍在跑 PRNG 空转（0x2002F4 每圈 263 cycles x 8,865 圈）。
  设备上由 `hot_block_prng` 原生 C 承担，**不是**宿主成本热点，但它占掉了 guest 的时间轴预算。

### 3.2 139 cycle/像素：对得上，但要分两条路径

用 A 的代价表把 0x207CA3-0x207CC4 逐条相加（`tools/r6b/blitcost.py`）：

| 路径 | 指令数 | cycles/像素 |
|---|---|---|
| 存像素（非键色） | 30 | **137.7** |
| 键色 0x07E0（跳过 0x207CB0-0x207CBA 共 11 条） | 19 | **38.0** |

- 任务书的 **139 cycle/像素** 与实测 137.7 差 0.9 % —— **成立**（缺口应是循环退出那一轮的 `jae` 分支）。
- 一次切换的平均值是 **124.9 cycles/像素**，比 139 低 10.1 %；算术上对应 **12.8 % 的像素是键色**
  （(137.7 - 124.9) / (137.7 - 38.0) = 12.8 %）。
- 所以 `N x 139` 只在「全部像素都要写」时成立；直接乘 N 会高估 10 %。

### 3.3 与设备实测的一致性检查

- 设备 LONGF（`docs/AUDIT_SWITCH_2026-11-26_R6.md:123`）：`us=73484 dblk=6926 dins=59747`
  → 73.5 ms 跑完 1.6 M guest cycles = **21.8 M guest cycles/s**。
- 本报告：一次切换 **6.40 M guest cycles / 4 帧**；设备上同样 4 帧 约 4 x 73 ms = **292 ms**，
  原机 66.7 ms → **慢 4.4 倍**（独立复算 73.5 / 16.67 = 4.41），与 R6B 框架给的倍数一致。

## 4. Q3：时钟界面稳定态每秒重画多少像素 / 窗口形状

### 4.1 设备日志的算术

blitpx 18,414/s、pushpx 18,189/s、fillpx 9,111/s，除以整屏 9,216：

| 量 | 值 | 除以 9,216 |
|---|---|---|
| blitpx/s | 18,414 | **2.00 屏/s** |
| pushpx/s | 18,189 | **1.97 屏/s** |
| fillpx/s | 9,111 | **0.99 屏/s** |

→ **每个 guest 秒把整块 96x96 重画两遍**（一次带常量填充做底，一次不带），即 **2 Hz 整屏重绘**。
**推测**：两次分别是「底图填充 + 精灵」和「时间数字/边框叠加」。这是算术推断，不是直接观测。

### 4.2 窗口形状（实测：从 ST7735 模型的 CASET/RASET/RAMWR 重建）

| 场景 | 窗口 | 面积 | 该窗口实际推的像素 |
|---|---|---|---|
| 上电 logo 整屏 | (0..95, 18..113) | 96x96 | 9,216（= 1.0 遍） |
| 切屏主带 | (0..95, 42..113) | 96x72 | 24,096（= 3.49 遍） |
| 切屏补带 | (0..95, 90..113) | 96x24 | 2,304（= 1.0 遍） |
| 启动 logo 局部 | (0..95, 18..41) | 96x24 | 1,056-2,304 |

**结论：时钟界面从不「只刷数字那一条」** —— 每次重绘都把 96x72 或 96x96 的窗口整块（甚至多遍）推一遍。
这就是为什么「秒针跳一下」在设备上也是重活：0.5 s 一次 x 2.4 M guest cycles。

### 4.3 每次整屏重绘的 guest 成本（用 3 的单价推算）

    一次整屏（9,216 px）：blit 9,216 x 124.9 = 1.151 M
                          + push 9,216 x 63.2 = 0.582 M
                          + fill 9,216 x 54    = 0.498 M
                          + 乘法/其他          约 0.15 M
                          约 2.38 M guest cycles = 1.49 个 guest 帧

2 Hz x 2.38 M = **4.8 M guest cycles/s = 96 MHz 的 5 %**，稳定态 guest 侧毫无压力
（与设备 90 M cycles/s、56 fps 自洽）。**问题 100 % 集中在一次性的整屏重绘与大面积移动那几帧。**

**未验证**：模拟器里切到时钟界面后**不再自动走时**（seed 0x0CB0=1 后 55 s 内 LCD 推送 0 像素，
`tmp/r6b/C/frames.csv`）。**推测**：ROM 在切屏/按键流程里会清掉 0x0CB0。本节的稳定态数字来自设备日志 + 算术。

## 5. Q4：「大面积画面元素移动」用的是什么原语

### 5.1 原语判定：键控 blit 进 96-word 行缓冲，再由推送循环刷窗口

- 常量填充 0x005B1E：整次切换只有 **7,728 cycles = 143 个像素（0.12 %）**。
  → **「大面积移动」不是「常量填充刷背景 + 局部 blit」**，填充只在带首擦一次底。
- 键控 blit 0x207CA3：9,240 次迭代，目标地址**恒在 0x07BA-0x081A**（97 个 word）。
  `dstmax=0x081A` = 0x7BA + 96 → 目标是**一行 96 像素的 RAM 行缓冲**；每行末尾由推送循环把这一行/一整带
  刷进 ST7735 窗口。`[bp+4]` 的 bias 实测出现 0/24/48/72 四种，正好是 24 行一带的 4 个子带偏移
  （`tmp/r6b/ip1/blits.csv` 早期的 (bias, dstmax) 组合）。
- 推送 0x005B4A：26,496 次 = LCD 像素数，63.2 cycles/像素（实测 1,674,216 / 26,496）。

### 5.2 精灵/字库数据在 flash 里的地址区间（从 src 指针来源反推）

`[bp+7]/[bp+8]` 是 DS:offset 的 24 位源指针，blit 每像素 `src++`
（`dbgtest/dasm_207c.txt:24-28` 的 `r3 += 01 / r4 += 00, carry` + `[bp+07]/[bp+08]` 回写）。
实测一次切换里 src 落在三簇（`tmp/r6b/B/blits.csv`）：

| 簇 | 地址区间（guest 24 位字地址） | flash 内字节偏移 | 用途（推测） |
|---|---|---|---|
| A | 0x2618CA - 0x26360A | 0x123F94 - 0x126C14（约 7.3 KB） | 场景底图/地貌切片 |
| B | 0x29E000 - 0x29FEAA | 0x13C000 - 0x13FD54（约 7.8 KB） | 数字/文字字模 |
| C | 0x34D5BE - 0x34D70E | 0x29AB7C - 0x29AE1C（约 0.3 KB） | 图标/小精灵 |

（guest 字地址 → flash 字节 = (addr - 0x200000) x 2，见 `emu/gpce4.cpp:505` 的直接映射窗口。）

- **一次大面积移动读多少字节**：9,240 次 `read16(src)` = **18,480 B 约 18.1 KiB**（4 帧内）；
  单帧最大 4,494 px = **8.8 KiB**。
- 另有少量 src 落在 0x00003B（RAM，`tmp/r6b/B/blits.csv` 帧 245 的 `src_min`）——
  **推测**是「把 RAM 行缓冲当源再 blit 一次」的合成操作。

### 5.3 一次切换的宿主数据 cache 压力（定量）

    18.5 KiB / 32 B = 578 条 cache 行
    578 x 约 300 周期（DIO，R5 5.4）= 173 k host cycles = 1.08 ms `160 MHz
    即「3.49 遍重推、每遍重新 miss」放大到 2,017 行 = 605 k = 3.8 ms

→ 占 4 帧 292 ms 的 **0.4 %-1.3 %**。**数据读不是「慢动作」的主因。**

## 6. Q5：要做到「和原机一样快」需要多少 guest cycles/s

### 6.1 硬算术

- guest 侧这次切换固定要 **6.40 M guest cycles**（4 个 guest 帧，由指令流决定，宿主无法压缩）。
- 原机 96 MHz → 6.40 M / 96 M = **66.7 ms**。要观感一致，宿主必须在 66.7 ms 内跑完 6.40 M guest cycles：

      >= 96 M guest cycles/s（重绘场景，不是平均）

- 宿主单核 160 MHz ⇒ 允许的宿主成本：

      160 M / 96 M = **1.67 host cycles / guest cycle**（红线）

- 现状（设备 LONGF 73.5 ms / 1.6 M）：21.8 M guest cycles/s = **7.34 host cycles / guest cycle**，差 **4.4 倍**。
- 稳定态已经 1.4（90 M cycles/s，`docs/AUDIT_PERF_2026-11-26_R5.md:20`）。

**换算成「每条 guest 指令的宿主成本」更便于落地：**
6.40 M guest cycles / 1.48 M 条指令 = 4.3 CPI；宿主侧 292 ms = 46.7 M host cycles
⇒ **31.6 host cycles / guest 指令**。要达标（66.7 ms）⇒ **7.2 host cycles / guest 指令**。
换句话说：**重绘路径上的每一条 guest 指令都必须按「原生 C」的价格执行**（PRNG 原生块现在约 3.4），
AOT 分发的 30-35 host cycles/指令是唯一的差距来源。

### 6.2 由 guest cycles 占比得到的优先级

| 改动 | 覆盖的 guest cycles | 换成原生实现（<=2 host cycles/guest cycle）可省 |
|---|---|---|
| HLE 推送循环 0x005B4A | 26.2 %（1.67 M） | 1.67 M x (7.34-2) = **8.9 M host cycles = 56 ms** |
| HLE 乘法 0x005F8B | 6.5 %（0.42 M） | 0.42 M x 5.34 = **2.2 M = 14 ms** |
| blit HLE 已存在，但**计费偏高 11 %** | 18.0 % | 见 7.2 |
| 填充 0x005B1E | 0.12 % | 可忽略 |
| PRNG 忙等 | 34.5 % | 已是原生块，无收益（只是 guest 空转） |

三项合起来约 70 ms，292 → 约 222 ms；距离 66.7 ms 仍差 3.3 倍。
**要一次到位只有两条路**：(a) 把 0x5B4A / 0x5F8B / 0x207A00-0x207D00 全部 HLE 且不计入 AOT 分发；
(b) 把 AOT 分发压到 <=7 host cycles/指令（R5 6 的尾调/回边超块、aot_step 内联属于这条路，但预算是 4 倍差距，
微优化到不了）。**我的判断：先做 (a)，它是唯一能把 292 ms 打进 100 ms 以内的单项。**

## 7. 建议改动（含预期收益与风险）

1. **HLE 推送循环 0x005B4A-0x005B8F（最高优先）**
   - 做法：与 `hle_blit_key` 同构 —— 入口检查 `[bp+x]` 计数与源/目标，把「RAM word → 2 字节 SPI2 写」
     用 C 循环一次做完，按 63 cycles/像素计费。
   - 收益：省 1.67 M guest cycles 的 AOT 分发 = **56 ms / 292 ms（-19 %）**。
   - 风险：**预算切分**。PC 侧 `SLICE_CYCLES=2000`（`emu/main.cpp:29`）意味着 63 cycles/像素时一次最多连跑
     31 个像素就得让出 slice；设备侧要按 `m_icount` 预算分段（`emu/unsp_glue.cpp:1071` 已有写法）。
     另外 HLE 必须逐字节复现 `st7735.cpp:188` 的 data_w 语义，否则 GRAM 与窗口指针会偏。

2. **修正 blit HLE 的计费（低成本、必须做）**
   - `emu/unsp_glue.cpp:1047` `AOT_HLE_BLIT_CYCLES_PER_PIXEL 139`：实测非键色 137.7、键色 38.0、平均 124.9。
     设备上 HLE 无条件按 139 计费 ⇒ **blit 密集场景 guest 时钟比原机快约 11 %**（不是慢），
     并且 12.8 % 的键色像素被多收约 101 cycles。
   - 收益：纠正时间轴（观感与相位），外加约 0.13 M guest cycles（约 1 ms）。风险：改计费会改 PRNG 相位
     （见 1.1），必须重跑 `--save-flash` 逐字节对拍。

3. **HLE 乘法 0x005F8B 或降级为查表**
   - 6.5 % 的 guest cycles，CPI 6.35（全场景最高）。若调用点确实是行段地址计算，可在 HLE blit/push 入口里
     用加法定标替代乘法。收益约 14 ms；风险：该例程可能被别的路径复用，先补 xref。

4. **不要追「数据 cache」**
   - 定量见 5.3：578 条 cache 行约 1 ms。R6 0.2.3 的方向即使做满也补不上 292 ms 的 1 %。
     若仍要做，先量 `hle_blit_key` 的 src 分布（5.2 给了三簇地址，可直接比对）。

5. **切屏「逐帧可见」可以单独消掉（可选）**
   - 4 帧重绘是 guest 行为，宿主不能拆帧；但可以在重绘期间**保持上一帧内容**（pending 窗口/双缓冲），
     把「黑条/半屏」的中间态藏掉，用户感知从「慢慢擦过去」变成「闪一下」。
   - 收益：观感，不改 fps；风险：需 96x96x2 = 18 KB 暂存（DRAM 余 88 KB 可承受，但与 R5 5.2 的整窗异步 blit 抢预算）。

## 8. 我没验证的部分（请按此打折）

1. **没有上机**：本会话无 USB（只有 COM1）。设备侧数字全部引自 `docs/AUDIT_SWITCH_2026-11-26_R6.md` 的 LONGF 行。
2. **模拟器复现不了时钟界面的「走时」**：seed 0x0CB0=1 后 55 s 内 LCD 推送为 0（4.3）。
   稳定态的 18 k px/s 只能靠设备日志 + 算术（4.1），不是观测。
3. **合成误差**：`counts` 里有 146,815 条指令（9.8 %）的 PC 在 `costs` 表里没有（解释器跑法没执行到），
   其周期未计入；表中 1.6 % 的「其余」就是该缺口的残差，所以 0 的百分比是 98.4 % 口径。
4. **事务对场景敏感**：`--clock-frame` 从 120 改成 300，同一按键序列的重绘量从 26,400 变成 56,479 像素
   （`tmp/r6b/C/frames.csv`）。本报告一律用 seed`120 的场景（与 HANDOFF 记录的进时钟序列一致）。
5. **`dst_max=0x9416`（帧 245）超出 4 KiB RAM**，落在 0x004000+ 的 ROM 只读区（写被丢弃，
   `emu/gpce4.cpp:571`）。我没判定这是 ROM 的正常路径（例如「只取色不落盘」的探测遍）还是我得出的
   `[bp+6]` 采样点在某个嵌套 pass 里失配。**推测：后者**，因此 0 的 blit 像素数（9,240）按「下限」使用。
6. **没做静态反汇编**：0x207CA3 的逐条语义引自既有产物 `dbgtest/dasm_207c.txt`（非本轮生成）；
   0x005B1E/0x005B4A 的循环边界来自 `emu/aot_blocks.c:15568/15768` 的块划分与
   `aot_b005B1E/aot_b005B4A` 里的 `0x3092` 写。没有逐条手验 0x005B4A-0x005B8F 的 14 条指令。
7. **「3.49 遍」的解释**只有算术巧合支持（24,096 = 3.5 x 6,912），没有调用栈证据。
