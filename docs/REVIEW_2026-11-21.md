# 方向性审查：digimon-color-passport（2026-11-21）

审查范围：docs/ 全部交接文档、emu/ 与 firmware/digicore-c3/ 的实现、tools/aot.py 发射器、
dbgtest/ 全部日志与 PC 对拍结果。结论只依据可复现的数字，推测处显式标注。

---

## 一、结论先行

1. **大方向没错**：整机可执行代码 <10 KB、762 个基本块、无间接跳转、无自修改代码
   （docs/COVERAGE.md），静态重编译是 C3 上唯一能到 60 fps 的路线，换解释器/换硬件都不是。
2. **实现走偏了**：`tools/aot.py` 生成的不是「重编译代码」，是**把解释器逐条指令展开成直线 C**。
   每条 guest 指令仍然走 `c->r[]` 内存数组、`aot_op()` 通用路径、逐条 `cyc += n`，
   产出约 15 条 RISC-V / 60 B 机器码（经典重编译是 4–8 条 / 16–32 B）。
   这是「60 fps 只在静止时存在」的根本原因，比超块、IRAM、超频都更根本。
3. **KPI 错了**：项目一直以「静止 58.8 fps」当成功标准。用户 m02375 原话
   「你说的60fps，只在画面静止时存在，这毫无意义」已经点名。真实指标应是
   **动画段 p95 帧时间、输入到画面延迟、连续 60 秒 frame_drops 计数**。
4. **有几个零成本/低成本的杠杆完全没拉**：flash QIO 模式、IRAM 热块、图形 HLE。
5. **「错位」问题代码里声称已修，用户仍反馈存在** —— 需要一次 PC/设备同帧对拍来定性，
   不能继续靠猜。

## 二、用日志重建的真实画像

数据源：`dbgtest/stable.log`（静止稳态）、`dbgtest/lat2.log`（换屏/按键/移动）。

| 指标 | 静止 | 动画/换屏 |
|---|---|---|
| guest_fps | 58.8 | **9.5 – 13.5**（峰值段） |
| AOT 块执行 / 帧 | 762 | **12,789**（17 倍） |
| guest 指令 / 帧 | 8,305 | **128,800**（15.5 倍） |
| 单帧 guest 执行时间 gmax | 12.2 ms | **105–211 ms** |
| guest_pct | 68% | 91–92% |
| blitmax | 1.9–2.6 ms | 1.7–3.3 ms（占比 <9%） |
| frame_drops 累计（kmax） | 0 | **233–387** |

两个关键比值：

- **块数涨 17 倍，指令数只涨 15.5 倍**：静止时 guest 大量时间耗在 64 Hz 节拍的
  忙等循环里（被 `spin_collapse` 折叠，不产生块调用）；动画时 guest 在跑真实逻辑，
  每帧 12,789 次块分发。**HANDOVER §6 拿静止态的 762–1,826 块/帧做超块推算，
  低估了动画态的真实分发量一个数量级。**
- **105 ms/帧 ÷ 128,800 条 = 815 ns/条 = 130 个 CPU 周期/条**。
  目标 60 fps 是 16.67 ms/帧，即 **每条 guest 指令只能花 20.7 个 CPU 周期**。
  当前超支 6.3 倍。

按 `880 周期/块` 与 `60 周期/条`（HANDOVER 实测 + 机器码反推）拆 105 ms：

- 块分发：12,789 × 880 = 11.25 M 周期 ≈ **70 ms（67%）**
- 指令体：128,800 × 60 = 7.7 M 周期 ≈ **48 ms（46%）**
- 两项之和略超 105 ms，说明 880 的 bench 是热态、且两项有重叠（880 里含一部分指令体）。
  **量级结论不变：分发是大头，指令体是第二大头，两者都必须砍，只砍一个到不了 60 fps。**

## 三、方向性错误（按严重度）

### 3.1 把「AOT」做成了「内联解释器」

`emu/aot_blocks.c` 里的典型一条 `mov r1, #0x4800`：

```c
uint16_t r0v = (uint16_t)c->r[1];   // 死初始化
uint16_t r1v = 0;                    // 死初始化
uint32_t r2v = 0;                    // 死初始化
r0v = (uint16_t)c->r[1];            // 重新 load
r1v = 0x4800u;
{ const uint32_t lr = aot_op(c, 0x9, r0v, r1v, true);
  if (lr != AOT_NO_WRITE) c->r[1] = (uint16_t)lr; }
cyc += 4;
```

`aot_op` 虽是 `static inline`、GCC 会常量折叠掉 switch，但：
- 每条指令仍从 `c->r[]` 内存 load 源操作数、store 目标 —— **没有寄存器分配**；
- 每条指令仍有 `cyc += n` 与块内的 `AOT_IH` 占位；
- 每个块是独立函数，分发走「查页表 → 函数指针 → 序言/尾声 → 返回」；
- 代码 830 KB 全在 flash XIP，16 KB ICache 装不下，块间跳转持续 miss。

**重编译的定义是「把 guest 的寄存器生命周期映射到宿主寄存器」，当前实现一条都没做。**
正确形态应是每个块开头把 `r0..r7/sr/sp` 收进局部变量、块内直接做 ALU、块尾一次写回、
一次计费；GCC 自然把它们分配到 RISC-V 寄存器，每条 guest 指令落到 3–5 条 RISC-V。

### 3.2 「已排除」清单的结论被错误前提污染

HANDOVER §6 列了「扩块表、MIN_NATIVE_INSNS 1→4、-Os、强制补 miss PC、内部 for(;;)」，
其中：
- `MIN_NATIVE_INSNS 1→4`「fps 不动」：在指令体占 46%、分发占 67% 的前提下，
  只改块的最小长度当然不动 —— **这不能证明超块无效，只能证明单改一个参数无效**；
- `-Os` 只 +0.6 fps：反过来证明**瓶颈不是代码密度，是每条指令的执行路径长度**；
- `for(;;) 连跑块` 21.56 fps 但饿死 collapse：说明分发开销真实存在（+13 fps），
  只是实现方式破坏了 64 Hz 节拍 —— **这是「分发是主项」的直接证据，不该被列为排除项**。

### 3.3 IRAM 只做了块代码，没做查表

先更正上一版报告的错误：**IRAM 热块不是「只停留在注释」，而是已经实现并在跑**。

- `tools/aot.py:67-76` 读 `AOT_IRAM_LIST`，`:669-676` 生成 `AOT_IRAM static void aot_bXXXXXX`（ESP_PLATFORM 下 `#define AOT_IRAM IRAM_ATTR`）；
- `tools/sync_c3_emu.py:139-146` 用 `tools/coverage/out/aot_iram_dev60.txt` 启用它，注释写明「top 60 覆盖 97% 分发、约 48 KB」；
- 生成物 `aot_blocks.c` 里实测 59 个 `AOT_IRAM` 块；`.iram0.text` 91,096 B / `iram0_0_seg` 321,296 B（28%）。

**但只做了一半。** `emu/aot.h:270-312` 的 `aot_lookup` 每次分发都要：

1. 用 64 槽页缓存（`g_aot_pg_tag/ref`，在 DRAM）定位 `AotPageDesc`；
2. 读 `d->fn[slot]` —— **`d` 本身和 `fn/cnt/cyc` 三张表都在 flash**，只有缓存里的指针在 DRAM。

也就是说：**块代码进了 IRAM，取指省了；查表还在 flash，每次分发至少一次 XIP 读。**
`g_aot_desc[]` 只有 60–80 项 × 12 B ≈ 1 KB，整体进 IRAM 毫无压力；热点页的 `fn[256]`
（1 KB/页）按块 census 选 top 10–20 页，再花 10–20 KB。

另外，HANDOVER 的「880 周期/块」是推算值，**从未实测分解过**。要先做一次测量（GPIO 翻转
或 `stage=prof`），把「查表 / ctx 准备 / call / 块体 / 返回」分开，否则后面所有优化都是在
猜一个没量过的数。

### 3.4 flash 是 DIO 80 MHz，不是 QIO

`sdkconfig.defaults:5` `CONFIG_ESPTOOLPY_FLASHMODE_DIO=y`。C3 的 XIP 取指走同一 SPI 控制器，
DIO 只有 2 条数据线，**ICache line 填充时间翻倍**。8 MB XMC flash 支持 QIO，
改一行 `CONFIG_ESPTOOLPY_FLASHMODE_QIO=y` 即可，零代码风险。HANDOVER 全文未提。

### 3.5 没有版本控制

3.5 MB 生成代码 + 十余个 patch 脚本 + 当天多次「改了显示 → 画面崩溃 → 回滚」，
全靠手工。任何一次优化都可能静默破坏 guest 语义，而正确性依赖 PC 对拍的 682,005 条指令——
**生成器一改，必须重跑四个对拍窗口，否则等于裸奔**。这不是风格问题，是复现能力问题。

## 四、遗漏的技术方案（按 ROI 排序）

| # | 方案 | 预期收益 | 成本 | 风险 |
|---|---|---|---|---|
| 1 | **发射器重写：块内寄存器局部化 + 块尾计费** | 指令体 60→15–20 周期/条，整体 2–2.5× | 2–3 天 | 语义偏差，PC 对拍兜底 |
| 2 | **超块：线性块合并 762→200、12,789→3,000 块/帧** | 分发 70→17 ms，整体 2× | 2 天 | 与 1 叠加才有意义 |
| 3 | **IRAM 热块（top 60–95）** | ICache miss 归零，1.3–1.5× | 半天 | 链接脚本/段属性 |
| 4 | **flash QIO** | XIP 带宽 ×2，10–20% | 一行 | 无 |
| 5 | **图形 HLE**（sprite blit / 清屏 / 文字渲染） | 动态指令再砍 30–40%（推测，未测量） | 3–5 天 | 像素对拍可验证，HLE 可开关 |
| 6 | **多编译单元 + 链接顺序按热度排** | ICache 局部性 +5–10% | 半天 | 无 |
| 7 | **双缓冲 + DMA 异步 blit** | 省 2–3 ms/帧（<9%） | 1 天 | 低，优先级低 |
| 8 | **C3 超频 200–240 MHz** | 1.25–1.5× | 1 天 | PLL/ flash 时序，无 IDF 支持，仅作最后手段 |
| 9 | 换 ESP32-S3 | 单线程 2.2×，屏幕 135×240 硬伤 | 重做板 | 已评估，不推荐 |
| 10 | 全程序反编译重写（762 块 → C） | 理论 100×，工作量 >> 收益 | 数月 | 仅作 AOT 彻底失败后的备选 |

**1+2+3+4 组合的算术**（105 ms 基线）：

- 分发：12,789 → 3,000 块，每块 IRAM 内 200 周期 → 0.6 M 周期 = **3.75 ms**
- 指令体：128,800 × 18 周期 → 2.3 M = **14.5 ms**
- 合计 18.3 ms + blit 3 ms = 21 ms → **48 fps**；
- 再把指令体压到 12 周期/条（真正的寄存器分配）→ 1.55 M = 9.7 ms，
  合计 13.4 ms + blit = **16.4 ms → 60 fps 达标，余量 0.3 ms**。

**结论：C3 上 60 fps 可达，但必须做完 1–3，且指令体要做到 ≤12 周期/条。
HANDOVER 的「超块理论 50 fps」低估了指令体，实际单做超块只能到 20–25 fps。**

## 五、三个用户症状的归因

### 5.1 按键迟滞接近 1 秒

不是输入通路的 bug。按键注入 `kPressFrames=2`、20 ms 轮询；guest 自己去抖要连续 4 帧按下。
动画段 10 fps 时 4 帧 = 400 ms，加渲染与下一次 blit，接近 1 秒。**这是帧率的下游症状。**
60 fps 后 4 帧 = 66 ms，自然消失。不需要单独改按键逻辑。

### 5.2 放置后冻结约 5 秒

`app_main.cpp:802` `kFrameBudgetUs = 200 ms`：单帧 guest 执行超过 200 ms 就整帧丢弃、
不补帧（`s_frame_drops++`）。lat2.log 的 `kmax=233–387` 就是累计丢帧数。
动画段 gmax 已达 131–211 ms，部分场景越线 → 连续丢帧 → 画面停住。
**根因仍是慢；不是显示路径。** 可在慢速期把 budget 提到 400 ms 减少冻结，
但那会让按键延迟更糟——不解决根本问题。

### 5.3 数码兽移动时「左右错位」

代码注释（`app_main.cpp:429-433`）声称修过 stride bug：「the right half of every odd panel
row was stale - that is the misalignment that showed up whenever a sprite moved」。
用户仍反馈存在，三个候选，按可能性排：

1. **SPI 面板无 vsync 的撕裂**（代码自己承认 `this panel has no vsync`）。
   分块刷新时上半屏与下半屏来自不同 guest 帧，精灵移动时表现为边缘错位。
   若属实，无硬件解（ST7789P3 的 TE 引脚未接），只能缩小单次传输跨度或降刷新区域。
2. **guest 侧渲染问题**：PC 模拟器上用同一 ROM 跑移动场景，看是否复现。
   若 PC 也错位 → 是 MAME 模型/ROM 行为，不是移植 bug（FEASIBILITY 已记录
   「参考帧视频仍有 MAME 自身滚动/错位」）。
3. **blit 修复未覆盖 rot≠0 路径**：`rot_map` 分支与直写分支是两套代码，
   只验证了一套。

**必须先做一次同帧对拍**：PC 模拟器在指定帧号 dump `fb[]`，设备在同一 guest PC/帧号
dump 同一区域，逐像素比。这比继续改代码猜有效。

## 八、P0 实测结果（2026-11-21 21:00–21:30）

三项改动真机实测，两项成功、一项失败。协议：esptool 分段写 bootloader/分区表/app，不碰 0x210000 的 ROM 分区；每次刷完抓 45–50 s 串口日志。

| 改动 | 结果 | 数据（dbgtest/） |
|---|---|---|
| flash QIO | **失败，已回滚 DIO** | ROM 用 QIO 读 bootloader 时 XMC 的 QE 位未置位 → TG0WDT_SYS_RST 复位循环，必须重新置 QE 才能再试（qio_real.log） |
| fn/cyc/cnt 合并成单表 | **无收益** | guest_pct 68→67，gmax 12.2→12.0 ms（ent1.log）——说明 flash 查表不是瓶颈 |
| dispatch 路径进 IRAM | **成功，单项最大** | guest_pct 67→**26**，gmax 12.2→**5.2 ms**，guest 执行 11.3→**4.0 ms/帧**，fps 58.8→**60.00**（iramdisp.log、iram2.log） |

第二项无收益、第三项一次砍掉 65%，两者合起来说明一件事：**瓶颈不是查表，是取指**。ot_lookup 三次 flash 读换成一次没人感觉得到，而把 execute_run / ot_step / ot_lookup / spin_collapse / wait_loop_collapse 整体搬进 IRAM（UNSP_HOT = IRAM_ATTR，emu/unsp_glue.cpp:11-21）立刻把每帧 guest 时间从 11.3 ms 压到 4.0 ms。此前「IRAM 热块」只搬了 59 个块体，调度器本身仍在 flash 里，每次块派发都要重新走一遍 XIP 取指。

按此重算：静止场景每帧 646 块 / 6,900 条指令，4.0 ms = 640 K 周期 → **93 周期/guest 指令**，块体与调度器都已在 IRAM 内，剩下的是发射器本身的质量（约 15 条 RISC-V/指令、c->r[] 内存往返）。**下一个杠杆是寄存器局部化，不是超块。**
