# 数码暴龙彩屏机模拟器 — 重新制定的技术路线

日期：2026-11-22
范围：本仓库 digicore-c3 固件（ESP32-C3 + GPCE4064B）
立场：**不继承既有结论**。本文的每一条判断要么有本机实测，要么有可复现的推导；与历史文档冲突处明确写出冲突。

---

## 0. 一页结论

**三件事同时做，互不阻塞：**

| 线 | 内容 | 解决用户哪条要求 | 预期 | 风险 |
|---|---|---|---|---|
| **A（主线）** | 三个热区的 HLE：定点乘加库、`render_band` 整函数、忙等折叠 | 画面卡顿 | 砍掉 86% 的 guest 指令数 | 中（正确性） |
| **B（主线）** | 代码生成器局部重写：寄存器钉住 + 尾调用链 + lazy flags | 画面卡顿 | 110 → 30~40 主机周期/指令 | 中（工程量） |
| **C（独立线）** | 按键链路重做：切片级采样 + 时间消抖 + 中断式注入 | **按键无延迟** | 337 ms → ≤20 ms | 低 |

**A+B 并联后重绘帧从 116 ms 压到 17~25 ms**，即 40~60 fps 且逻辑帧 100% 满速。
**C 单独就能做完，不等 A/B**，改完立刻能感觉出来。

**明确不做的事**：换 ESP32-S3、上 JIT、双缓冲整帧 DMA、改 kCpuClock、跳帧。理由见 §6。

## 1. 把"手感"翻译成硬指标

用户原话是手感，工程上必须量化，否则无法验收：

| 用户表述 | 硬指标 | 当前实测 | 差距 |
|---|---|---|---|
| 按键无延迟 | 按下到 guest 读到按键 ≤ **20 ms** | **116~337 ms**（见 §3.3） | 6~17× |
| 画面切换流畅、无卡顿 | 重绘帧 guest 执行 ≤ **16.7 ms**（60 Hz 满帧） | **116 ms**（8.6 fps 实测） | 7.0× |
| 运行不拖慢 | 游戏速度（guest cyc/帧 == 1,600,000）= **100%** | 静止 97% / 重绘 **14%** | — |
| 不必纠结纸面 fps | **不允许**用跳帧、拉长帧预算、降低 kCpuClock 来伪造 fps | — | — |

退路定义（可接受的次优）：**逻辑帧 60 Hz 满速、显示帧 30 fps**。养成类小屏游戏肉眼几乎无差，且游戏速度正确。这条退路要求重绘帧 ≤ 33 ms。

## 2. 现状确诊：钱花在哪

### 2.1 三个场景的实测（设备 COM4，docs/PERF_2026-11-22.md）

| 场景 | fps | 游戏速度 | guest 占用 |
|---|---|---|---|
| 静止 | 58.0–58.1 | 97% | 23–33% |
| 单次界面切换 | 22–29 | 37–48% | — |
| 连续重绘（狂按方向键） | **8.6** | **14%** | **92%** |

### 2.2 成本分解

- 每帧 guest 预算 1,600,000 cycles（96 MHz ÷ 60）。
- 重绘帧 **154,451 条 guest 指令 / 12,744 次块调度**。
- 端到端 **110 主机周期/guest 指令**；AOT 路径 63，解释器路径约 424。
- 60 fps 需 17.3 周期/指令，30 fps 需 34.5。
- 渲染路径（脏矩形 + SPI 推屏）只占 **1–5%** CPU。**瓶颈 100% 在 guest 指令执行**，这一点没有争议。

### 2.3 指令都在哪（同一份 trace，7.94 M 条）

| 区域 | 指令占比 | 主机周期占比 |
|---|---|---|
| 内部 ROM `0x005F8B` 定点乘加库（17 条指令） | **39.8%** | ~15.6%〔推算〕 |
| 绘制区 `0x207900–0x207D40`（`render_band`，724 条） | **46.2%** | 17.3% |
| `0x230321` 忙等 | 5.5% | — |
| push 循环 | — | 1.1% |
| 解释器路径（AOT 未覆盖的块） | — | 15.0% |
| AOT 其余 | — | 51% |

〔推算〕标记：PERF §4 只直接给出后四项（17.3 / 1.1 / 15.0 / 51），乘加库的 15.6% 是由 100% 相减得出，不是独立测量值。

**注意这张表里指令占比与周期占比严重不成比例**：乘加库吃 39.8% 的指令却只花 15.6% 的时间。这说明它的块体代码极短、每指令周期极低。反过来，"AOT 其余 51%" 只对应 8.5% 的指令 —— **那 51% 的时间花在少数 8.5% 的指令上，这才是真正贵的代码**。

## 3. 推翻旧结论：四条被误判的事实

### 3.1 寄存器局部化**从未在设备上生效**

- `tools/aot.py:578 emit_body(img, entry, loc=False)` 有局部化模式，`main()` 第 731–754 行在 `LOOSE` 且块够长时采用局部化版。
- 用同一组环境变量重跑生成器得到 `tmp/aot_probe.c`，自报 **`localised blocks: 985 (>= 4 insns)`**。
- **但设备固件跑的 `firmware/digicore-c3/main/emu/aot_blocks.c`（3,906,743 B）里 `AOT_LOAD_REGS` / `AOT_SAVE_REGS` 各出现 0 次。**
- 对照 PC 侧 `emu/aot_blocks.c` 有 511 次 `LOAD_REGS`。

=> 设备上那条"每条 guest 指令读写 `c->r[]` 两次"的代价，一直白付着。**重跑一次生成器即可免掉，这是全项目性价比最高的一个动作。**

### 3.2 `always_inline` 是空操作，别在这上面浪费时间

本机实测（60 块切片，`tools/measure_aot.py`）：

| 版本 | 块体字节 | 指令数 | jalr |
|---|---|---|---|
| 局部化基线 | 20,580 B | 7,358 | 164 |
| 五个辅助函数加 `always_inline` | 20,568 B | 7,367 | **164** |

变化在噪声内。`aot_op` / `aot_rd` / `aot_wr` 本来就被内联了。那 164 次 `jalr` 全部来自 `bus_rd` / `bus_wr` 的**冷路径**（`address > ram_limit`），静态条数含冷路径，不代表执行。**已回滚该改动。**

### 3.3 按键延迟的真正来源：**消抖按帧计**

- `app_main.cpp` 主循环：`update_buttons()` **每帧只调一次**。
- `kPressFrames = 2` —— 消抖要"连续 2 帧稳定"。
- 重绘帧 116 ms → 单帧内采不到；连续两次采样要 232 ms；加消抖 = **约 337 ms**。

这不是性能问题，是设计错误：**用帧数当时间单位**。在任何帧率下这都是错的。**改它不需要等任何性能优化落地。**

### 3.4 IRAM 这条路已经用尽，不是"还没试"

`aot_blocks.c` 里 `AOT_IRAM` 出现 63 次（60 个块 + 宏定义），即 60 个热块**已经在 IRAM**。PERF §3 的"14 热块 IRAM 无变化"是这 60 块之上的边际实验。别再投。

## 4. 主线 A：三个热区的 HLE

HLE 的原则是**按"调用次数 × 每次固定开销"排序，不按指令占比排序**。历史上已验证：忙等折叠（5.5% 指令）7.69→14.15 fps；push 循环（1.1% 周期）+12.6%；PRNG 块 1.09→7.82 fps。**小改动拿到大倍数的先例都在 HLE 这一侧。**

### A1. 定点乘加库 `0x005F8B`（先做，最容易赢）

已经从 `emu/aot_blocks.c:16887-17047` 完整解码出 17 条指令：

```
push bP, sr, pc          ; 压栈
bp = sp + 1              ; 建帧
从 [bp+3]..[bp+6] 读 4 个 16-bit 参数
1 次 MUL uu + 2 次 MUL ss（带 lres -= a<<16 符号修正）
高低半字分别累加（不传进位）
pop bp, sr, pc
```

关键点（逐条踩过）：
1. **不需要 int64**：只有 16×16→32。
2. 符号修正逐字照抄：`if (b & 0x8000) lres -= a << 16; if (a & 0x8000) lres -= b << 16;`
3. 两个半字的累加各自按 16 bit 回绕，**互不进位**。
4. 出口 SR 由 `pop` 恢复 —— 这是最大的坑，别按"ALU 更新标志"处理。
5. `0x005F8E` 是去掉序言的同体（15 条），一起 HLE。

验收：参数 {0, 1, 0x7FFF, 0x8000, 0xFFFF, 随机} 的笛卡尔积 + 20 万组随机，比对 R1–R7 / SP / SR / 写内存集合，要求 **100% 逐位一致**。

预期：39.8% 的指令消失，主机周期省 10~16%（区间取决于上面那条推算的准确性，P2 上机后以实测为准）。

### A2. `render_band` 整函数 `0x2079FC–0x207D29`（收益最大，风险最高）

已逆向完成（`tmp/draw_region_report.md`，1,290 行）：

- 函数签名 `void render_band(u16 y0, u16 h)`，724 条指令，栈帧 0x3D 字。
- 精灵记录表：`0x0608` 起 36 条 × 12 字；`0x07B8` = 记录数；`0x07B9` = 脏带掩码；`0x07BA–0x0819` = 96 字行缓冲（96 个 RGB565 像素）。
- 记录字段：`+0` gfx/命令字（`0xFFFE` = 纯色填充）、`+1` 填充色、`+2` s16 x0、`+3` y0、`+4` w、`+5` h、`+6/+7` src_lo/hi、`+8` enable==1、`+9` x1、`+0x0A` y1。
- 脏带刷新器 `0x207992` 按掩码触发 `render(0x00,0x18)` / `render(0x18,0x30)` / `render(0x48,0x18)`，共 96 行。

分段执行占比：正向键控 blit（33 条）**37.4%**、剔除+裁剪前奏（429 条）9.1%、blit 前奏 1.6%、行推屏 0.5%。

**做法：影子实现。** guest 路径照跑，HLE 并行算一遍，逐像素比对；全等后再摘掉 guest 路径。回归用 `dbgtest/fb_f60.bin` + 600 帧 + 随机输入序列，改比 RAM/显存快照 + 帧缓冲哈希。

预期：绘制区 46.2% 指令消失，省 17.3% 主机周期；若连行推屏一起接管，可到 25%。

### A3. 忙等折叠

`0x230321` 占 5.5% 指令。已有 `spin_collapse` / `wait_loop_collapse` 框架，确认覆盖后直接收益。

## 5. 主线 B：代码生成器局部重写

### 5.1 诊断：不是 IPC 低，是每条 guest 指令执行的机器码条数太多

- 设备块 `_ZL11aot_b207CA3P6AotCtx` = **352 B**（`nm --print-size`），覆盖 6–7 条 guest 指令；按 RVC 平均 2.5 B/条折算 ≈ 140 条指令 → **约 21~23 条 RV32/guest 指令**〔估算〕。
- 63 周期 ÷ 23 条 = **2.7 周期/条（IPC 0.37）**。
- 同平台可到 IPC 0.8 → 同样 23 条只需 29 周期。

**两条独立的药**：把 23 条压到 13 条（B1/B2），把 IPC 从 0.37 抬到 0.8（B3）。

### 5.2 B1. 寄存器钉住 + 尾调用链（63 → 52~56）

`recomp/README.md` 的上界证明：同一个 guest 直线函数，**1.98 主机周期/guest 指令**（C3 真机实测，三组 golden 校验全 PASS）。它快的原因只有一个 —— `recomp/unsp_state.h:54-199` 的 25 个 `op_*` 全是 `static inline` 且 TU 极小，于是全部展平、无 call、无 `c->r[]` 中转。

落地方式（子 agent 调研 + 本机实测支撑）：

- 每个 guest 基本块一个**独立 C 函数**，块内 `r1..r15` 用宿主局部变量钉住。
- 块间**尾调用**而不是返回 dispatch 循环。本机实测：`riscv32-esp-elf-gcc 14.2.0` 在 `-O2`（sibcall 默认开）下，四个互尾调的基本块链接松弛后**全部变成单条 2 字节 `c.j`，整个二进制 0 个 `ret`、0 个 `call`，连栈帧都不建**。限制：必须 `noinline`、跨 TU 要 LTO。
- 这同时消掉了 PERF 里 dispatch 的 68 周期/块（6 周期/指令）。

### 5.3 B2. lazy flags（23 → 13 条）

`S` 标志的语义是 `bit16(v) != bit15(r0 ^ r1)` —— **依赖两个源操作数**，所以不能只缓存结果 `v`，必须缓存 `(v, r0^r1)`。缓存起来，等真正有人读 SR 时再算。实测代码里绝大多数 ALU 结果的标志没人读。

配套：每指令一次 `icount` 内存 RMW 要改成块尾一次性扣（LOOSE 模式已经这么做了，确认 985 块版本里没有回退）。

### 5.4 B3. 访存快路径（抬 IPC）

- DS 页基址 + 无分支索引，消掉每次访存的 `address <= ram_limit` 比较。
- 冷路径（`bus_rd`/`bus_wr`）保持现状，用 `__builtin_expect` 标到 unlikely 段。

### 5.5 明确的工程约束

- **切片优先**：全量 3.9 MB TU 的 `-O3` 编译超过 12 分钟（实测），任何代码生成实验都走 60–100 块切片。
- **每块单独 TU 或分片 TU**：内联预算按 TU 分配，762 块挤在一个 TU 里就必然有函数被踢出内联。这是当前病根的机制成因。
- **先编译后测量**：`tools/measure_aot.py` 已能按真实编译命令编译任意切片，输出块体字节、指令数、jal/jalr/ret、助记符直方图。改生成器后先跑它，再上设备。

## 6. 独立线 C：按键链路重做（**立刻可做，不等 A/B**）

三处改动，互相独立：

1. **采样移到切片边界。** `update_buttons()` 从"每帧一次"改为 `run_guest_frame()` 内部每个 `kSliceCycles`（0.5 ms）调一次。最坏延迟从"整帧"变成 0.5 ms。
2. **消抖改成时间，不按帧。** `kPressFrames = 2` → `kPressStableUs = 8000`（8 ms 稳定即认）。在 8.6 fps 下这直接把 210 ms 变成 8 ms。
3. **注入不等帧边界。** 按键状态一变，就在下一个切片边界写 guest 的 IO 端口，当前帧内立即可见。

改完后的延迟预算：采样 0.5 + 消抖 8 + 传递 <1 = **≈9 ms**，远优于 20 ms 指标。**且与 A/B 是否落地无关。**

## 7. 硬件与平台：留在 C3

- **C3 的天花板**：160 MHz 单核 RV32IMC，IPC 上限约 0.8–0.9，16 KB I-cache。按 13 条 RV32/指令 × 1.3 周期 + HLE 砍 86% 指令，重绘帧可到 17~25 ms。**够。**
- **换 S3 的真实收益是 1.87×**（同代码整数加 127→238 MOPS，WLED issue #4206 基准），不是纸面的 240/160=1.5×。**S3 的整数除法快 25.7×**（C3 约 34 周期/次），本作除法用得少，吃不到。
- **脚位不兼容**：C3 QFN32 vs S3 QFN56，换芯等于重开板。
- **JIT 在 C3 被系统锁死**：`CONFIG_ESP_SYSTEM_MEMPROT` 默认 y，`MALLOC_CAP_EXEC` 直接不可用；要做 JIT 必须关它放弃 W^X。而且同平台的公开先例（esp32-emu-turbo 的 68000 dynarec）是 **78 周期/指令 vs 解释器 46 —— JIT 更慢**。**不做。**
- **同行参照**：FoloToy plays/2247 是 tamaemu 的 C3 移植，S1C33 每指令固定 `cycles += 16`，C3@160 MHz 折合 **≤139 宿主周期/指令**才能 1×。本项目当前 110，已经在它之上；目标是 30–40，那就是它的 4 倍。

## 8. 阶段与验收

每个阶段必须全绿才进下一步。基线工具（已有）：`emu_validate` 100% / `cyc_diff` 0 / `fb_f60.bin` 帧哈希 / `--save-flash` 零字节。

| 阶段 | 动作 | 目标指标 | 验收 |
|---|---|---|---|
| **P0** | 冻结基线；C 线（按键）先落地 | 按键延迟 ≤20 ms | 秒表 + 高速摄影 |
| **P1** | 重跑生成器拿 985 块局部化 | 110 → ~90 周期/指令 | 帧哈希不变 |
| **P2** | A1 乘加库 HLE | 90 → ~75 | 20 万组参数逐位一致 |
| **P3** | B1 寄存器钉住 + 尾调用链 | 75 → ~50 | 帧哈希不变 |
| **P4** | B2 lazy flags + B3 访存快路径 | 50 → ~33 | 帧哈希不变 |
| **P5** | A2 `render_band` 整函数 HLE | 重绘帧 ≤17 ms | 600 帧 + 随机输入逐像素一致 |

到达 P5 即 60 Hz 满帧、游戏速度 100%。若 P4 后只到 25 ms，先按"逻辑 60 + 显示 30"的退路交付，再攻 P5。

## 9. 风险与不确定项

**必须承认的不确定：**
1. `render_band` 整函数 HLE 的工作量没有把握 —— 724 条指令里有裁剪、翻转、色键三条路径，其中翻转/翻转 blit 在当前 trace 里执行率为 0（不在 AOT 块表内），行为未经验证。**先做影子实现，别直接替换。**
2. `0x005F8B` 的调用点是否覆盖全部乘加场景，尚未统计全部 151 个置脏调用点的调用图。
3. 63 周期/指令里"块尾 2 条调度 + return"的真实占比，只有切片静态数据，没有逐指令的运行时剖面。P3 前建议先补一次 per-block 周期剖面。
4. PERF §3 那张判负表里"超块合并上限 5%"与"dispatch 689 = 68 查表 + 532 块体"自相矛盾（68/689 = 9.9%，不是 5%）。**P3 的尾调用链会同时验证这一点**，无需单独实验。

**已确证、不要再讨论的：**
- 双缓冲整帧 DMA 上限 1.5 ms，需 16 KB DRAM，余量不够。
- `kBlitEvery=2`、页缓存、紧凑块表进 DRAM、`-Os`、QIO、关 C3_SPLIT —— 全部实测无收益或负收益。
- 改 `kCpuClock` 只改切块粒度，不改吞吐；跳帧会让游戏变速。
- 静止时不应向屏发任何字节（这块 ST7789P3 无 vsync/TE）。

## 10. 与既有成果的关系

**继承**（已验证可靠，不重做）：硬件映射、`render_band` 逆向、`0x005F8B` 解码、覆盖率分析、所有判负结论、`recomp/` 的静态重编译上界。

**推翻**：
1. "C3 上 30/60 fps 都不成立" —— 该结论建立在 110 周期/指令之上，而其中至少 20% 是**局部化从未生效**造成的白付。P1 之后重估。
2. "需重写代码生成器"方向对，但**优先级错**：HLE 砍的是指令条数（86%），代码生成器砍的是单条成本（2–3×），两者乘积才是答案，而 HLE 先做、风险更低。
3. "按键延迟要靠提帧率解决" —— 错。它是消抖按帧计造成的设计错误，与帧率无关。
