# 进展记录 2026-11-23：黑屏根因与修复

> 本文是 dde3901 之后的第一手排障记录。目标症状：**游戏画面部分全黑；设置菜单能开，关闭后屏幕残留**。

## 1. 结论先说

两个症状是两个独立 bug，均已修复并上机验证。

| 症状 | 根因 | 修复 |
| --- | --- | --- |
| 开机后游戏画面黑（部分或全黑） | gueststate 快照只存 CPU + 8 KB RAM，**不含 SoC 外设寄存器，也不含面板 GRAM**。恢复后 INT2_Ctrl 回到 reset 值 → IRQ7 永不投递 → 游戏 64 Hz 帧节拍死等；同时 ST7735 复位后 fb 全黑，而 guest 只推"它认为变了"的 tile，一块都不推 | 快照加 `Gpce4State`（SoC 寄存器）；新增 `fbsave` 把可见区 28672 B 像素单独持久化到 save 分区，恢复时先灌回 fb |
| 关掉所有输入 18 秒后画面发黑、任何按键都叫不醒 | ROM 的空闲路径写完 `System_Sleep`(0x3036) 就一路执行到 0x5340 之后的**空白区**，之后不再读按键 | 按键即硬件唤醒：`Gpce4::wake_from_sleep()` 重放上电序列（清寄存器、从 ROM 头 0x4017 取复位向量），RAM 不动，宠物还在 |
| 关闭设置菜单后屏幕残留 | 菜单卡片 x=10..309 比 blit 窗口 x=32..287 各宽 22 px；`menu_present()` 整宽 320 推面板，关闭后 `blit_frame()` 只重推窗口，两条 22 px 卡片色永远留在屏上 | 关闭分支调用 `panel_clear_side_margins()` 把两条边带填黑 |

顺带纠正一个长期误判：**`FB_CRC 38699DC5` 就是"fb 全零"的哈希值**（FNV-1a over 16384 个 uint16 = 0）。之前把它当"验收通过"的判据，实际是"一个像素都没画"。


## 2. 排障关键证据

### 2.1 冷启动是好的，只有快照恢复后黑

- 擦掉 save 分区冷启动：`gueststate: no usable snapshot` → `BOOT_OK first non-blank guest frame at 20 frames, pc=007ca3`，画面是完整 Digimon Color logo，`FB_CRC 62C4882E`。
- 有快照时复位：`resumed at pc=200343 sr=0020 sp=0ff5`，但 `fb` 全零、`blitmax=0 rows=0`。

### 2.2 中断、定时器、按键、HLE 全部正常

- `[irq] line7=1 / line7=0` 交替 24 次，`m_cpu` 非空。
- `[tick] stat=20000200 int2=0205 any=1 isr=790`（14 s ≈ 56 Hz）→ 64 Hz 节拍正常。
- 按住 A 时 `read16(0x3000)=FFF7`，ROM 把 `0x0852` 置成 `0x0008` → 按键链路通。
- `X 0` 关掉 render_band HLE 后 fb 立刻全黑 → HLE 是画面唯一产生路径，工作正常。

### 2.3 "标题画面按键推不动"不是 bug

emu 上 `--press "8:900:960"`、`"0008:900:960"` 都停在 `PC=200343`（logo 界面），画面不变。与设备完全一致，是 ROM 自身行为。

## 3. 代码改动清单

### 3.1 新增 `firmware/digicore-c3/main/fbsave.h` / `fbsave.cpp`

save 分区（0x490000，128 KiB）重新划分：

```
0x00000  gueststate 环形 5 x 12 KiB   (0x0F000)
0x0F000  fbsave 一块 32 KiB           (0x08000)
0x18000  saveimg 两槽 16 KiB          (0x08000)
```

- header 32 B：`magic 'DGFB' / version / reserved0 / bytes / crc / reserved1[4]`。
- `fbsave_load()` 分两遍流式读（第一遍 256 B 窗口算 CRC，第二遍落盘），因为 C3 只剩 ~10 KiB DRAM，放不下 28672 B staging buffer。

### 3.2 `emu/gpce4.h` / `gpce4.cpp`

新增 `Gpce4State`（magic `'GPC4'`、version 1）与 `Gpce4::save_state()` / `restore_state()`，逐字段镜像 `reset()`。`restore_state()` 末尾调 `update_interrupts()` 重新驱动中断线。

**LCD 窗口不恢复**：只恢复 `display_on / sleep / madctl / colmod`，`posx/posy/command/pixellatch` 一律清零，窗口强制全屏 0..127。原因是恢复半开的 CASET/RASET 会让后续像素落到 y<8 或 y>=120 的隐藏带（第一版就是这么错的）。

### 3.3 `app_main.cpp`

- `struct SnapBlob { internal_unsp_state cpu; Gpce4State io; uint32_t fb_crc; }` → payload 276 → **280 B**（长度变化自动让设备上的旧坏快照失效）。
- `snapshot_machine_state()` 里 `s_snap_blob.fb_crc = save_panel_frame();`。
- `restore_machine_state()` 里先 `load_panel_frame()` 再 `s_force_full = s_blit_repaint_all = true;`，日志加 `frame=restored|none`。
- 前置声明 `static bool load_panel_frame(void);`（`case 'U'` 要用）；`case 'U'` 外层加花括号，否则 `jump to case label` 报 11 处错。

### 3.4 `gueststate.h`

`GUESTSTATE_RECORDS` 8 → 5（腾出 36 KiB 给 fbsave）。

### 3.5 睡眠态防护（`app_main.cpp` + `emu/gpce4.cpp`）

- `Gpce4::wake_from_sleep()` 从 inline 空实现改成真正的上电重放：清 16 个寄存器、`m_vectorbase = 0x4010`、PC 取 ROM 头 `read16(0x4017)`（实测 0x480D），再补 `m_enable_irq/fiq`、`m_fir_move`、`m_pri`、`m_divq_bit`。`m_cpu` 为空时只清 `m_asleep`。
- `app_main.cpp` 新增 `static void guest_reset_cpu(void)`（原 `guest_init()` 里那段复位代码抽出来），`guest_init()` 与唤醒路径共用。
- `update_buttons()` 里 `if (bits != 0xffff && s_soc.asleep()) s_soc.wake_from_sleep();`。
- `snapshot_machine_state()` 开头 `if (s_soc.asleep()) return;`——绝不持久化掉电态（否则恢复出来是个再也不会读按键的 CPU）。
- `restore_machine_state()`：快照里 `asleep != 0` 或 PC 恰好为 0（旧版误存），都改成重放上电，日志追加 `wake=reset`。

### 3.6 卡片 alpha 混合（`menu.cpp`）

- 新增 `blend565(dst, src, a)`（`a` 为 0..256）与 `kShadowPx = 12`、`kCardAlpha = 230`(90 %)、`kShadowAlpha = 102`(40 %)。**90 % 是照抄参考板的 `bg_opa = LV_OPA_90`（230/255）**，不是估计值：`C:\Users\DuWeisi\digimon-passport\firmware\digimon-passport\main\digimon_app.c:2698-2701`。
- `card_line()` 先在卡片矩形外 12 px 范围内做 `blend565(s_row[x], 0x0000, 102)` 投影，再把卡片内改成 `blend565(s_row[x], kPanelBg, 250)`——游戏画面透出来，和参考板的观感一致。
- 代价：推送一屏 320x240 从"平坦填充"变成"逐像素混合"，**一次菜单刷新约 127 ms（那一秒 host_fps 7.9），之后菜单静止时 57 fps 不动**。

### 3.7 菜单串口抓帧（`N` 命令）

菜单是**直推面板**、从不写 `fb[]`，所以 `T` / `L` 永远看不到设置界面。为了不靠肉眼验收，加了：

- `menu.cpp` 的 `menu_present()` 里，`s_capture > 0` 时把每行的 `s_row` 以 `B <band> <y> <160 个 4 位 hex>` 打到串口（隔行隔列，整帧约 7 s @ 115200）。
- `menu_set_capture(int frames)` + 控制台 `N <frames>`（`0` 关闭）。
- 注意：**必须读 `s_row` 而不是 `strip`**——`strip` 交给 `display_draw_bitmap()` 之后内容不可依赖，第一版读 `strip` 抓回来全 0。
- 配套 `tmp/menu_capture.py`：`N 10` → 长按 B → 收行 → 拼 160x120 → 放大成 320x240 PNG。

实测抓到的面板内容与 `tmp/menu_final.png` 的桌面预览一致，也证明 `panel_clear_side_margins()` 之外的渲染路径没有问题。

### 3.8 比例字间距（`menu.cpp`）

5x7 点阵本身不是问题，问题是**按 6 列定宽排版**：`I` 和 `M` 占一样宽，整行看起来像打卡纸。参考板是真正的比例字。

- 新增 `glyph_span(c, &first, &last)`：扫该字符 5 个列字节，取非零列的首末（全空回 0..4）。
- 新增 `glyph_advance(c)`：空格 6 px，其余 `(last-first+1) * 2 + 2`（墨迹宽度 + 一列字距）。
- `text_scanline()` 改成 `x += glyph_advance(code)` 推进、`px = x + (col - first) * 2 + sx` 定位；`text_width()` 同步累加。
- 效果：`AUTO SAVE` 从 216 px 缩到 ~150 px，居中标题与右对齐数值自动跟着收紧。
- 桌面预览脚本 `tmp/menu_final_preview.py` 完全复刻当前 `menu.cpp`（alpha + 阴影 + 比例字 + 背景 upscale），输出 `tmp/menu_final.png`，不用烧写就能看版式。

### 3.9 七行菜单与 SAVE OUT / SAVE IN（`menu.cpp` / `menu.h` / `app_main.cpp`）

参考板的 320x240 截图（`digimon-passport\milestones\2026-11-02_menu-ux-v2\screenshots\menu_7rows.png`）是 **7 行平铺**（`ROM / SHELL / BRIGHT / VOLUME / AUTO OFF / SAVE OUT / SAVE IN`），不是后来那版"5 行一级 + 二级面板"。本项目照的是前者。

- `menu.h`：`MENU_ITEMS = 7`，新增 `MENU_IDX_SAVE_OUT`、`MENU_IDX_SAVE_IN`，`MENU_IDX_ABOUT` 挪到 6；新增 `enum { MENU_ACTION_NONE, MENU_ACTION_SAVE, MENU_ACTION_LOAD }` 与 `int menu_take_action();`。
- `menu.cpp`：`s_action` 承接命令行的请求，`menu_press_b()` 在 SAVE OUT / SAVE IN 上只置 `s_action`（不碰 flash），`menu_take_action()` 读后清零。
- `app_main.cpp:1162` 的菜单分支在派发完 A/B/C 之后 `switch (menu_take_action())`：SAVE → `snapshot_machine_state()`；LOAD → `restore_machine_state()` + `menu_close()` + `s_blit_repaint_all = true`。这样 `menu.cpp` 不需要知道快照怎么存。

## 7. 第二轮（13:20 之后）：用户实测反馈四条

用户回来实测否掉了上面"全部完成"的结论，指出四条：

1. 设置界面没问题（已认可）。
2. **时钟界面长按 A 无效**。
3. **16 秒熄屏唤醒后没有直接回游戏**，出现游戏自己的 CONTINUE/RESET，要重设时间，进度也像是没存。
4. **游戏画面没有变化，还是主画面偏左**。

### 7.1 已修复：熄屏唤醒不再丢状态

原来的 `wake_from_sleep()` 重放上电序列（清 16 个寄存器 → 从 `read16(0x4017)=0x480D` 取复位向量），等于让 ROM 冷启动，所以用户看到 CONTINUE/RESET。

现在改成 **park**：`Gpce4::system_sleep_w()` 只在 `m_asleep = true` 之后把 PC 直接弹到 `m_sleep_resume_pc`，`wake_from_sleep()` 只清标志；背光由 host 的 `update_sleep_backlight()` 负责。

- `app_main.cpp` 的 `kGuestResumePc` 从 **0x230321**（标题画面等待循环，park 过去会退回 logo）改成 **0x200300**：时钟界面的热点循环在 `0x200307`–`0x20031C`（trace 实测约 321 031 次/秒），入口是 `0x2002F4` 的三趟延时循环。
- 上机：`[gpce4] sleep resume point 000000 -> 200300` / `first System_Sleep write = 5555` / `panel dark after 16002 ms idle`；空闲 26 s 画面仍是完整时钟；按键唤醒后 `pc=200343`，**日志里没有 `resumed at` 也没有 `BOOT_OK`**，画面仍是时钟 → 不再冷启动、不再出现 CONTINUE/RESET。

### 7.2 顺带修正：按键极性本来是反的

`gpce4.h:226` 的老注释写的是"bit value 1 = released, 0 = pressed (active low)"，`update_buttons()` 也照这个实现（`bits &= ~kPortB1` → `0xFFF7`）。

emu 逐值实测（`GPCE4_AOT=0 --seconds 10 --press "<v>:60:66"`）：

| 注入值 | 结果 |
| --- | --- |
| `0x0008` | 进时钟界面（`0:00:00`） |
| `0xFFF7` | 停在 logo |
| `0xFFD7` | 停在 logo |

即 **ROM 把 PORTA 当高有效位域读**。`update_buttons()` 已改成按下时 `held |= kPortB1`、`bits = held`。改后串口日志为 `port=0008`（长按出现 `0028` = A+C），`Z 3000` 按住时返回 `0008`。

### 7.3 仍未解决：设备上 guest 不吃按键

即使端口值已经正确，设备上 ROM **仍然停在 logo**，不进时钟。已逐项排除：

- ROM 字节一致：`Z 005306=970B`、`Z 00530C=5555`、`Z 00530E=3036`、`Z 005010=970B`，与 `roms/internal_rom_221017a.bin` 逐字相同。
- flash 内容一致：`Z 200000=DA88`、`Z 201000=9898`、`Z 210000=0000`、`Z 230000=DA88`、`Z 300000=07E0`，与 `saves/flash.bin` 逐字相同。
- `[0x0850]`–`[0x0853]` 全 0；`Z 3000` 按住时确实返回 `0008`。
- AOT 开关无关：`-DC3_NO_AOT=1` 后帧日志 `aotb=0 aoti=0 guest_fps=58.43`，A+C 仍无效。
- 注入时长无关：6 / 20 / 40 / 300 帧都试过，均无效。
- emu 侧同一 ROM、同一 flash、同一注入值 `0x0008` 在任何时刻（第 60 / 180 / 360 / 600 帧）都能进时钟 → **ROM 逻辑本身没问题**。

下一步方向（未做）：在 emu 里给"读 0x3000"打点，比对设备与 emu 在同一 guest 时刻的 `[0x0852]`/`[0x0853]` 与 PC 序列；或直接在设备上 dump 一次 0x200300 附近的完整 RAM 与 emu 同刻 RAM 做 diff（`--bp 00200300 --bp-dump` 可取 emu 侧）。

### 7.4 UI 外壳：三方案样张（等用户拍板，未改固件）

参考板 `PROMPT-UI-carryover.md` 的外壳规格是按 **96×96 单色面板** 算的：三层外壳（well → rim → canvas）+ 192×192 画布（96 的 2 倍）+ HUD 横带。本机面板是 **128×128，可见窗口 128×112**，2 倍整数放大就是 **256×224**——在 320×240 上占掉 256 宽 224 高，**再没有空间塞三层外壳，也放不下 HUD 横带**。这是硬件约束，不是取舍问题。

`tmp/ui_mock.py` 渲染了三种布局（`tmp/ui_a.png` / `ui_b.png` / `ui_c.png`）：

| 方案 | 画面 | 外壳 | HUD | 代价 |
| --- | --- | --- | --- | --- |
| **A 现状** | 2× 256×224 居中 | 无 | 无 | 四周黑边，视觉上"偏左"的观感就来自这里 |
| **B 外壳** | 1.5× 192×168 | 三层齐全 | 底部三标签 | 非整数倍 → 缩放发糊；画面面积掉 44 % |
| **C 叠加**（推荐） | 2× 256×224 | 无 | 上下各 17 px 半透明条 | 不缩画面；HUD 压在画面顶部/底部各 17 px |

方案 C 的做法与 `PROMPT-UI-carryover.md` 里"别过 `lv_draw_sw` 缩放""canvas 分配失败=黑屏"两条硬约束不冲突：它不动 blit 路径，只在 `blit_frame()` 之后往面板上下各写一条 17 px 的 `#1B2417` @78 % 半透明条，再叠文字。代价是顶部 34 px 画面被盖住（时钟界面上方那排图标正好在 y=8..24，会被挡）。
