# Digimon Color / GPCE4 — 时间源与 RAM 0x0600..0x0607 逆向报告

> 范围：`roms/internal_rom_221017a.bin`（内 ROM，字地址 0x4000..0xFFFF）+ `roms/dmc_v1_base.bin`（8 MB SPI flash，字地址 0x200000..0x3FFFFF）。
> 手段：MAME 0.289 `dasm` 静态反汇编 + `mame.exe` trace/`gtime` 动态轨迹 + `emu/digicore.exe` 逐秒 RAM 快照 + flash 补丁实验。
> 未改动 `emu/` 与 `firmware/`；未烧写任何设备。

---

## 0. 结论速览

| 编号 | 问题 | 判定 | 证据强度 |
|---|---|---|---|
| A | 时间从哪来 | **SoC 内部 2 Hz 中断 + 纯软件计数**。没有 RTC 芯片，没有 I2C，没有读回任何时间寄存器 | 已证明 |
| A-补 | 外部芯片总线/从地址/寄存器图 | **不存在**。全镜像 IO 交叉引用里没有 I2C 端口，也没有任何非 flash/LCD 的 SPI 设备 | 已证明（负证据） |
| A-缺省 | 芯片"缺失"时的行为 | 开机 `0x2041C5` 把时/分/秒与使能位清零 → **停在 0:00:00 不动**（正是模拟器现在的表现） | 已证明 + 补丁实验 |
| B-1 | 谁写 0x0600..0x0607 | 唯一写者 `0x2002F4`（128-bit 移位/异或状态机），种子由 `0x2002CC` 在启动时写入 | 已证明 |
| B-2 | 值从哪来 | 既不是读定时器，也不是未初始化 RAM：它是"**忙等循环里被搅动了多少次**"的混沌函数 | 已证明（含实测迭代计数） |
| B-3 | 为什么 emu ≠ MAME | 0x0600..0x0607 差得天差地别 = 迭代次数不同（混沌放大）；而 0x0C86 / 0x0C9A / 0x0CB1 只差 **恰好 1 个 tick**，是快照采样落在 tick 边界两侧 | 已证明（1 s 与 5 s 两组数据） |

## 1. 任务 A：时间从哪来

### 1.1 中断向量表

`emu/main.cpp:192` 设 `cpu.m_vectorbase = 0x4010`；`ref/unsp/unsp.cpp:493` 取 `PC = read16(m_vectorbase + 0x08 + line)`，即 **IRQn → 0x4018+n**：

| 向量 | 地址 | 定时源（SoC） | 处理程序做什么 |
|---|---|---|---|
| IRQ0 | `0x4834` | timer_a 20 kHz（音频） | 空 `reti` |
| IRQ2 | `0x483E` | timer_c 1 kHz | 清 `0x3051` bit13，call `0x565A` / `0x5698` |
| IRQ3 | `0x484E` | 300 kHz | — |
| IRQ6 | `0x485D` | 2 kHz | 空 |
| **IRQ7** | **`0x486B`** | **INT2：2 Hz + 64 Hz** | **唯一的时间来源** |

SoC 侧这两个频率在 MAME 里是理想周期定时器（`ref/generalplus_gpce4_soc.cpp:140-141`：`timer_2hz` / `timer_64hz`），不是从某个 32.768 kHz 晶振分频建模的。

### 1.2 IRQ7 处理程序原文（`dbgtest/re/irom_full.txt`）

**这是整台机器唯一"感知时间流逝"的地方。** 没有任何地方去读 0x3033（Timebase）、0x3010..0x3016（timer 计数）来取时间。

### 1.4 设置时间：`0x204179`（时钟设置界面的"确认"）

**IO 寄存器只有三个：`0x3053`（INT2 使能）、`0x3054`（INT2 状态/清位）、`0x3033`（Timebase_Clear）。没有数据总线、没有时钟线、没有片选——所以不可能存在 I2C/SPI 的 RTC 芯片。**

### 1.5 清时间：`0x2041C5`（启动路径 `0x201E14` 调用）

把 `0x0CAF / 0x0CAE / 0x0CAD / 0x0CB0 / 0x0CB1 / 0x0CB2` 六个字全部写 0。**这就是"没有电池、没有 RTC 时"的退路：时间被定义为 0:00:00 且冻结，而不是读回 0xFFFF 或重试。**

### 1.6 时钟显示

| 地址 | 作用 |
|---|---|
| **`0x203F73`** | **画"真实时间"（RTC）**：从 `[0x0CAF]`/`[0x0CAE]`/`[0x0CAD]` 取时/分/秒填参数块（另有两个入参 = x、y 坐标）→ `call 0x203FE4` 画 `hh:mm`；随后把 x+8 与 `[0x0CAD]` 重新填块 → `call 0x204123` 画秒 |
| **`0x204843`** | **主界面每帧处理**：状态 `0x0C8A` 变化时重装 `0x0C87=0x42A`/`0x0C86=0x0C87`/`0x0850=0`/`0x0D04=0`，然后 `[0x0881]=[0x0CAD]`、`call 0x20701E`、`call 0x2025DB(0x0824)`、**`0x2048A1: call 0x203F73(0x17, 0)`**、`call 0x20267C`（提交） |
| **`0x2048D5`–`0x2048F2`** | **秒刷新判定**：`if ([0x0CAD] != [0x0881]) { [0x0881] = [0x0CAD]; dirty |= 1; }`；`if ([0x0CB2]) dirty |= 1;`（秒进位脉冲）→ `dirty&1` 时 `0x204925: call 0x203F73(0x17,0)` 重画 |
| `0x203D9E` | **设置时钟界面**入口（被 `0x200990`、`0x200224`、`0x2002B1`、`0x2003D2` 调用），`0x203DCE` 装载 `0x085C=0x0CAF`、`0x085D=0x0CAE`、`0x0C87=0x0FA0`、`0x0C86=0x0C87` |
| `0x203FAB` | 设置界面的画面：取 `[0x085C]`、`[0x085D]`，**秒位直接写死两个 digit tile `0x30 0x30`（"00"）**（`0x203FD4/0x203FD8: r3 = 30`）→ 所以设置界面的秒永远是 00 |
| `0x204123` | 十进制数字绘制（除以 10 调 `0x5D4D`，5 位循环，tile 基址 0x33） |
| `0x203FE4` | `hh:mm` 绘制 + 范围钳制（h>23→0、m>59→0、s>59→0），并做 12/24 小时判断（`0x203FFA: if h > 0x0B` 用 tile 基址 `0x0221`，否则 `0x0222`） |
| `0x203E9E` | 设置界面的按键状态机：state1 `[0x085C]++`（>0x17 归零）、state2 `[0x085D]++`（>0x3B 归零）、state3（`0x203F17`）调 `0x204179` 提交 |
| `0x209349` | **每秒刷新钩子**（不画时钟，处理到期/闹钟/存档等）：`if ([0x0CB2]) {...}`，被帧体 `0x230107`（每帧）和主循环 `0x23017E`（秒变化快路径）调用 |

**两类界面必须分清**（这是原始工单里最容易误判的地方）：

1. **主界面（状态 0x1C/0x1D）**：`0x204843` → `0x203F73` 直接读 `0x0CAF/0x0CAE/0x0CAD`，**显示的是会走的真时间**；刷新由 `0x2048D5` 的"秒变了"或 `0x0CB2` 触发。
2. **设置界面（状态 0x02）**：`0x203FAB` 读的是暂存 `0x085C/0x085D`，**秒位写死 "00"**；按键改时/分，按确认才 `0x204179` 写回 RTC。

`0x203F73` 的全部调用点（机器码扫描 `F060 3F73`，`tools/re/find_clock_draw.py`）：`0x2048A1`、`0x204925`、`0x204993`、`0x2049F8`、`0x204A5F`、`0x204ABF` —— 全部在 `0x2048..0x204B` 这一段主界面/菜单代码里，每一个后面都紧跟 `call 0x20267C`（提交帧缓冲）。

截图里那四格 `0:00 00 → 1:00 00 → 1:01 00 → 1:02 00` 属于第 2 类（设置界面）：中间那格是 `0x085D` 被按键 +1，秒位从头到尾都是硬编码的 `00`。所以"时钟在跑"是错觉——**在 `0x0CB0 == 0`（未设置时间）的情况下，RTC 根本不走**。

实测证据：`--autoplay` 跑到 5 s 时屏幕显示 `0:00 00`，RAM 里 `0x0CAF/0x0CAE/0x0CAD` 全 0；5.5 s 时屏幕变成 `0:01 00`，RAM 里 `0x085D=1` 而 `0x0CAE` 仍为 0 —— 屏幕上动的是**设置界面的暂存值**，不是 RTC。

### 1.7 反证：全镜像 IO 交叉引用（`tools/re/io_xrefs.py`）

| 镜像 | 出现的 IO 地址 |
|---|---|
| flash（142 处） | 0x3000–0x3007、0x3010/11/14/15/16、0x3022、0x3030、0x3033、0x3050/51、0x3053/54 |
| 内 ROM（113 处） | 上述 + 0x300C–0x300F、0x3012/13、0x3020、0x3035/36、0x3070/72、0x3094/95、0x30E0/E4/E5/E7 |

- 0x309x = SPI2（LCD），0x30Ex = SPI1（flash）。**没有第三个 SPI 设备，没有 I2C（GPCE4 根本没有 I2C 控制器）。**
- 0x3033 只被**写**（0x5555），从未被读回。

### 1.8 补丁实验（决定性）

把 flash 副本 `dbgtest/re/flash_rtc_on.bin` 的 `0x2041D7` 从 `0x9640` 改成 `0x9641`（即"清时间"函数里把 `0x0CB0 = 0` 改成 `0x0CB0 = 1`；文件偏移 0x83AE），然后：

```
emu\digicore.exe --load-flash dbgtest\re\flash_rtc_on.bin --autoplay --seconds 9 \
    --shot-dir dbgtest\re\shots_rtc --shot-every 30 --ram-at 6 --ram-dump dbgtest\re\rtc_on_t6.bin
```

结果 t=6 s 时：`0x0CAD(秒)=5`、`0x0CB1=1`、`0x0CB0=1`、`0x0CB2=0`。

**在完全没有任何外部芯片、也没有改动模拟器的情况下，只要把使能位置 1，软件 RTC 就从 0 开始以 1 Hz 走起来了。** 这就是"时间完全由 2 Hz 中断软件累加"的终局证据。

### 1.9 结论与推测

- **已证明**：时间源 = INT2 的 2 Hz 中断 → `0x0CB1` 半秒计数 → `0x5BE2` 每两拍加 1 秒 → `0x0CAD/0x0CAE/0x0CAF`。硬件接口只有 `0x3053` / `0x3054` / `0x3033` 三个寄存器。
- **已证明**：不存在外部 RTC 芯片；"芯片不存在"的分支就是 `0x0CB0 == 0` → `0x5BE2` 立即返回 → 时钟停在 0:00:00。
- **推测**：真机上 `0x3033 = 0x5555` 的作用是把 SoC 内部低频分频器相位清零，让 2 Hz 边沿与固件清 `0x0CB1` 的时刻对齐，避免首秒抖动。MAME 里 `0x3033` 只是 log/忽略，所以模拟器上第一秒可能比真机早/晚半拍。
- **推测**：真机断电后时间丢失（没有备份电池、没有写 flash 的时间戳），所以固件在启动时无条件清时间并要求用户设置——这与 `0x2041C5` 的启动调用点吻合。

## 2. 任务 B-1：RAM 0x0600..0x0607

所以初始状态 = `1333 0549 CD15 075B 55E5 159A 3BB5 1F12`，**与实测 t=200 ms 的 RAM 完全一致**（MAME 和 emu 都一样，说明此时还没被搅动过）。

等价 C：

```c

uint16_t hi = (uint16_t)(((t >> 24)        ^ (t >> 16)));   /* = ((t.hi>>8) ^ t.hi) */
W1 = W2; W2 = W3; W3 = W0;
W0 = ((uint32_t)(hi ^ (W0 >> 16)) << 16)
   | (uint16_t)(lo ^ (((W0 >> 16) >> 3) ^ (uint16_t)W0));
```

**实测校验（逐位对上）**：`--bp 2002F4 --bp-dump` 取到进入时的状态，`--bp 200343 --bp-dump` 取到执行完一次后的状态：

```
pre  : 1333 0549 CD15 075B 55E5 159A 3BB5 1F12     （= 种子，说明 t=200 ms 时还没被搅过）
post2: 45EA DCA3 55E5 159A 3BB5 1F12 1333 0549     （W1←W2、W2←W3、W3←W0、W0=0xDCA345EA）
```

公式算出的 `W0' = 0xDCA345EA` 与实测完全一致 → **步进语义已证明**（脚本 `tools/re/prng_check.py`）。

**含义**：这是一个 128-bit 的 xorshift 类伪随机状态。**它不是由 RTC 派生的**，也没有任何"读时间"的动作；它唯一与时间有关的输入是"循环什么时候停"（见 2.3）。

### 2.3 谁在搅动它（`tools/re/callers.py`，扫描 `F060 xxxx` 机器码）

| 调用点 | 上下文 |
|---|---|
| **`0x230321`** | 主循环里的忙等（原文见下），**在等下一个 64 Hz 边沿的整个空档里反复搅动** |
| `0x200C54` | 按键重复计时器 `0x081E` 归零时（`0x200C1A` 函数体内） |
| `0x200CDB`、`0x200CF6` | 另外两条按键/事件路径 |
| `0x20035B` | 同段初始化路径 |

主循环忙等原文（`dbgtest/re/flash_2302d0.txt`）：

```
230320: EE14      jmp 230335
230321: F060 02F4 call 2002f4       ; ← 搅一次 PRNG
230323: FE00      ds = 00
230324: 990C 0850 r4 = 0850
230326: 98E4      r4 = ds:[r4]
230327: 4840      cmp r4, 00
230328: 5E48      je 230321          ; 64 Hz 计数还是 0 → 回去再搅一次
230329: F140      int off
23032B: 990C 0850 r4 = 0850
23032E: 2841      r4 -= 01
230332: D8E3      ds:[r3] = r4       ; [0x0850]--
230333: F14E      fiq on
230334: F149      irq on
230335: FEA3 00E8 goto 2300e8        ; 回到帧体开头
```

**这就是"时间→随机数"的唯一耦合点**：不是读定时器的值，而是"在定时器下一次跳变之前，CPU 能挤进多少次迭代"。

### 2.4 实测：它到底被搅了多少次

用 `emu\digicore.exe --seconds 1.1 --trace dbgtest\re\emu_tr_t1s.tr --trace-start 1.0 --trace-seconds 0.02` 抓 20 ms 全指令流（476,714 条指令），按 PC 计数：

| PC | 次数 / 20 ms | 说明 |
|---|---|---|
| `0x2300E8`（帧体入口） | **2** | 20 ms 内 2 次；64 Hz 对应 1.28 次，取整后为 1~2 次，量级吻合 |
| `0x230321`（`call 2002f4`） | **6412** | 忙等循环迭代 |
| `0x2002F4`（PRNG 入口） | **6412** | 与上一行一一对应 |

换算：**每个 64 Hz 周期里 PRNG 被推进约 5000 次**（6412 / 1.28 ≈ 5010）。而帧体只跑 2 次，说明 CPU 时间几乎全花在忙等里：帧体（渲染/SPI，几十万条指令）→ 忙等搅 PRNG 直到 `0x0850` 变化 → 帧体 → …

**因此 0x0600..0x0607 的值 = "这 15.6 ms 里 CPU 挤进了多少次忙等迭代"的混沌函数。** 任何周期级的差异（中断响应延迟差几十个周期、slice 粒度、SPI/LCD 时序差几微秒）都会让迭代数差几十上百次，再被这个混合函数放大成完全不相关的 128-bit 值。

### 2.5 结论（B-1 / B-2 / B-3）

- **谁写**：只有 `0x2002F4`（+ 启动时的 `0x2002CC` 种子）。
- **是不是读定时器**：不是。它读的是 `0x0850`（64 Hz 软件帧计数）来**决定何时停**，而不是把定时器的值混进状态。所以既不是"cycle-accurate 读定时器"，也不是"未初始化 RAM"。
- **为什么 emu ≠ MAME**：
  - 200 ms 时两边的 8 个字**完全相同**，且用 `--bp 2002F4 --bp-dump` 取到的进入状态证明它**还是种子**（一次都没搅过）→ 代码路径、初值一致；
  - 1 s 时 MAME `2CBA 2622 EA99 C186…`、emu `5552 6CE3 F35E D3D4 A046 637A 5552 6CE3` → 完全无关，符合"混合函数 + 迭代次数差几千"的特征；
  - 旁证：MAME 在 t=20 s..50 s 这 8 个字**完全冻结**（`A2D6 A689 89E9 B6F7 131B 4574 0C0B D00B`，20 s 与 50 s 逐字相同），而 2 Hz 计数 `0x0CB1` 还在涨（0x28→0x32→0x3C→0x50→0x64）。此时 `0x0C88 = 0x1C`（不在启动那条 `0x230321` 忙等路径上），于是 PRNG 一次都不推进 —— 反证了这 8 个字的值就是"忙等迭代次数"的函数，与 RTC 无关。
- **对拍建议**：**不要**把 `0x0600..0x0607` 当成逐帧一致性判据。要么在比较时排除这 8 个字，要么在 `0x230321` 忙等循环里把 `call 2002f4` 打桩（跳过）——两者都会让逐帧 RAM 对比立刻干净。

## 3. 任务 B-2：0x0C86 / 0x0C87 / 0x0C9A / 0x0CB1

### 3.1 `0x0C86` / `0x0C87` = UI 倒计时（按键重复/超时）

- **递减点唯一**：`0x20068F`（被调度器 `0x200620` 在**每次状态处理函数返回后**调用一次）：

```
20068F: DA88      push bp, bp to [sp]
200690: 0B08 0001 bp = sp + 0001
200692: FE00      ds = 00
200693: 990C 0C86 r4 = 0c86
200695: 98E4      r4 = ds:[r4]
200696: 4840      cmp r4, 00
200697: 5E09      je 2006a2          ; == 0 → 直接返回
200699: 2841      r4 -= 01
20069B: 970B 0C86 r3 = 0c86
20069D: D8E3      ds:[r3] = r4        ; [0x0C86]--
2006A2: ...                            （尾部返回，略）
```

- **调度器**：`0x2005F3`（每帧由帧体 `0x23010B` 调用）→ 若 `0x0C88 != 0x0C89` 清 `0x081F` → 按 `0x0C88` 查 `0x200623` 处的 24 项跳转表（见 `dbgtest/re/ui_state_table.txt`）`call mr` → 返回后 `0x200620: call 20068F`。
- **重装点**：状态切换时 `0x0C87 = 0x42A`，`0x0C86 = 0x0C87`（0x2001B2/0x20023F/0x200B54 等十余处）；时钟设置界面用 `0x0C87 = 0x0FA0`（0x203DCE）。
- **消费点**：`0x2047CB`——`if ([0x0C86] == 0) { if ([0x0CDD]==0) return 10; else 重装并 return 11; } else return 0;`，即"这次按键是重复触发/超时触发吗"。
- **量级**：`0x42A` = 1066 帧 ≈ 16 s（@64 Hz）；`0x0FA0` = 4000 帧 ≈ 62 s。

> 注意：`0x0C86` 还被 flash `0x200020..0x200900` 的软件浮点/除法库当**暂存**反复读写（该区 157 处立即数引用），所以它的值偶尔会被 FP 运算污染。**这不是 bug，是编译器复用 RAM**——判读时要看上下文。

### 3.2 `0x0C9A` = 电池/充电检测的节拍计数器

`0x4F01`（帧体 `0x2300F5` / `0x2300FE` 调用，入参：`0x0C88 == 0x24` 时传 1，否则传 0）。摘要（**非逐字原文**，逐字反汇编见 `dbgtest/dasm_4ef0.txt`）：

```
0x4F0A: r4 = 0c9a / r4 = [r4] / cmp r4,0 / jne → [0x0C9A] -= 1 ; goto 0x4FBE
       否则：4 次 call 0x584C（ADC 采样）→ 平均 → call 0x5F0D → 与 0x33333AD3 做 32 位除法
       → 结果写 0x0C9D/0x0C9E → 与阈值 0x0C9F..0x0CA2 比较得出 0..5 的电池状态
```

即 **"隔 N 帧测一次电池电压"的倒计时**，与时间显示无关。

### 3.3 `0x0CB1` = 2 Hz 半秒计数

见 1.2：IRQ7 里 `++`；`0x5BE2` 里 `-= 2` 并进位一秒；`0x204179`（设时间）与 `0x2041C5`（清时间）里清零；`0x5320` 初始化段里补一次 tick。

### 3.4 emu 与 MAME 的差异：**恰好 1 个 tick**

| 时刻 | 变量 | MAME (`dbgtest/cov/A/ram_t*.bin`) | emu (`dbgtest/emu_ram_t*.bin`) | 差 |
|---|---|---|---|---|
| 1 s | `0x0C86` | 0x0401 | 0x0402 | 1 |
| 1 s | `0x0C9A` | 0x0016 | 0x0017 | 1 |
| 1 s | `0x0CB1` | 0x0002 | 0x0001 | 1 |
| 5 s | `0x0C86` | 0x0301 | 0x0302 | 1 |
| 5 s | `0x0C9A` | 0x0022 | 0x0023 | 1 |
| 5 s | `0x0CB1` | 0x000A | 0x0009 | 1 |

三个变量的偏差方向一致且恒为 1：**MAME 的快照正好落在 tick 之后，emu 的快照落在 tick 之前**。也就是说这些不是功能差异，而是**采样时刻落在 tick 边界的哪一侧**。逐帧对比时应当按"允许 ±1"来判定，或者干脆在同一个 `gtime` 边沿采样。

> 顺带：emu 侧从 t=2 s 起 `0x0CB1` = 3,5,7,9,0x0B,0x0D,0x0F —— 严格 2 Hz，说明 2 Hz 中断本身在模拟器里是准的。

## 4. 让模拟器读主机时间：最小改动建议（**未修改 emu/**）

因为硬件侧根本没有 RTC 寄存器，唯一可行的注入点是**直接写固件的时间变量**。改动点：

**文件**：`emu/main.cpp`
**位置**：帧循环内的 slice 循环 `while (cycle < frame_end)`（`emu/main.cpp:312` 起、`emu/main.cpp:338` 收尾）**之后**、截图逻辑（`emu/main.cpp:340`）之前
**依赖**：文件头加 `#include <ctime>`
**用到的符号**：`Gpce4 soc;`（`emu/main.cpp:182`）、`int64_t cycle`（帧内已模拟周期数）、`CPU_CLOCK`（96000000）、RAM 数组 `uint16_t ram[4096]`（`emu/gpce4.h:143`，`struct Gpce4` 默认 public；`emu/gpce4.cpp:459/486` 的 `read16/write16` 直接索引它）

```cpp
// —— 主机时钟注入（每帧，emulated seconds 换算成 wall clock）——
if (host_clock)
{
    static int64_t t0_wall = -1;
    if (t0_wall < 0) t0_wall = (int64_t)::time(nullptr);
    std::time_t now = (std::time_t)(t0_wall + cycle / CPU_CLOCK);
    std::tm lt{}; localtime_s(&lt, &now);
    const uint16_t s = (uint16_t)lt.tm_sec;
    if (soc.ram[0x0CAD] != s) soc.ram[0x0CB2] = 1;   // 让 0x209349 的每秒刷新跑起来
    soc.ram[0x0CB0] = 1;                             // RTC 使能
    soc.ram[0x0CAF] = (uint16_t)lt.tm_hour;
    soc.ram[0x0CAE] = (uint16_t)lt.tm_min;
    soc.ram[0x0CAD] = s;
}
```

**预期行为**：
1. 开机后屏幕上的时间不再是 0:00:00，而是**主机本地时间**；因为固件自己的 1 Hz 累加会被每帧覆写，所以即使模拟器跑得比实时快/慢，显示也永远等于 `启动时刻 + 已模拟秒数`。
2. `0x0CB2` 在主机的秒发生变化时被置 1，`0x209349` 的每秒 UI 刷新钩子照常触发，界面不会卡帧。
3. 固件自身的 `0x5BE2` 仍会每秒 `0x0CAD++` 并做 60/24 进位——因为我们每帧覆写，进位结果会被吃掉，不会产生双倍速。
4. 若固件在设置界面按下确认（`0x204179`），它会写自己的 h/m/s，但下一帧会被主机时间覆盖。**若希望保留用户的设置，把注入改成"只在 `soc.ram[0x0CB0] == 0` 时写一次"，并顺势把 `0x0CB0` 置 1。**

**替代（更"像硬件"的做法，**推测**）**：不改 RAM，而是在 `Gpce4::write16` 里给 `0x3053` 的 bit0 做一个"主机时间驱动的 2 Hz 相位"重写——但这需要改动 `emu/gpce4.cpp` 的定时器相位逻辑，且无法改变"时间从 0 起算"的事实，性价比远低于上面 8 行。**推荐上面的 RAM 注入。**
