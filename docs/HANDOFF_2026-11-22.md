## 3. 存档：完整可用

### 3.1 游戏怎么存

真机 8 MiB NOR 里两个 4 KiB 扇区 `0x7FD000`（主）/ `0x7FE000`（备），各一条 **92 字节**记录。
游戏**每 60.000 s** 整扇区擦一次再整条重写，主备**逐字节相同**。命令流
`SE → RDSR(05) → WREN(06) → PP(02)×92` ×2。**掉电容错游戏自带**，固件不需要事务。

### 3.2 固件侧

- `main/saveimg.h` / `main/saveimg.cpp`：双槽 **16 KiB** 步长、基址 `kBase = 0x18000`（前 96 KiB 让给 §3.5 的机器状态环），header 24 B（magic `DGSV` /
  version 2 B / page_count 2 B / sequence 4 B / crc 4 B / page_no[2]×4），`esp_rom_crc32_le`
- `SparseRom::overlay_export()` / `overlay_import()`（`main/emu/romstore.cpp`）
  —— **注意 `overlay_import` 里必须有 `m_writes++`**，少了就永远不落盘（踩过）
- `app_main.cpp` 的 `restore_save_image()`（在 `guest_init()` 里 `s_soc.reset()` 之后）
  与 `persist_save_image()`（主循环 `blit_frame()` 之后，静默 ≥1 s 落盘）
- `partitions.csv`：`roms 0x210000 0x280000` + `save, data, 0x41, 0x490000, 0x020000`（128 KiB）
- **烧 `digicore-c3-full.bin`（4,677,888 B = 0x476100）不会擦 0x490000 的存档分区**

### 3.4 重要事实：从空卡启动不会自动存档

PC 环缓冲（`aot_dump_pc_ring()`）证明：开机 17–18 秒后 `rflash` 归零，guest 停在内部 ROM
的 `0x5376` / `0x5251` 轮询循环里 —— **那是游戏在等按键，不是冻屏**。数据：`pa=0x3000` 掉到
642（按下），`r51`（`0x0851`）变 1，之后恢复。所以"10 分钟没写 flash"是正常的：没玩到存档点。
`W` 命令是注入式验证（写 overlay 页 `0x7FD`/`0x7FE`）。

### 3.5 机器状态快照（断电续档）

游戏从不写 flash（§3.4），进度全在 guest RAM 里，所以"断电续档"必须快照整机状态，
不能只镜像 overlay。overlay 通路继续留给 §3.2，两者共用同一个 `save` 分区。

- `main/gueststate.h` / `main/gueststate.cpp`：`save` 分区**前 96 KiB** 的 8 条环形记录，
  每条 3 个 4 KiB 扇区（`GUESTSTATE_RECORD_SIZE = 0x3000`）。header 32 B（magic `DGST` /
  version / `sequence` / `crc32` / `length_a` / `length_b`），payload 两段：
  `internal_unsp_state`（**160 B**）+ guest RAM（**8192 B**）。合计 8,352 B ≤ 12,256 ✓
- **不额外占 DRAM**：DRAM 只剩 10,416 B，8 KiB 暂存缓冲放不下，所以 CRC 用
  `esp_rom_crc32_le` 直接在调用方缓冲上分段累加，写盘分三次 `esp_partition_write`
  （header / CPU / RAM），写完回读 header 校验 sequence+crc
- 触发点：主循环帧边界。`debug_poll()` 只在 `run_guest_frame()` 之外被调用，所以 `D`
  命令与 60 s 定时都落在两条 guest 指令之间，`internal_unsp_state` 可整块 memcpy
  （`m_icount` 一起被保存，但 `execute_run()` 前会重设，无副作用）
- RAM 的 CRC 未变时跳过写入（宠物静止不动就不写 flash），每帧只判断一次时间差
- 磨损：60 s 一次 = 1,440 次/天 ÷ 8 个位置 = 180 次擦/位置/天 → 100,000 次寿命 ≈ 556 天
- 恢复后置 `s_force_full = true` 强制全屏重绘（ST7735 窗口状态与 guest RAM 不同步）
- 控制台 `D` 手动快照、`U` 手动恢复；`W` 仍只测 overlay 通路，两者互不影响
- 旧 `DGSV` v1 槽（64 KiB 步长）会失效 —— 里面只有 `W` 注入的测试图案，可接受

## 4. 声音：已通过（2026-11-22 20:05 实机听到）

### 4.1 硬件事实

- **ES8311 codec @ I2C 0x18**，I2C SDA=10 / SCL=7
- I2S `I2S_NUM_0`：MCLK=6 / BCLK=5 / WS=3 / DOUT=2 / DIN=4
- `BSP_I2S_PA_CTRL = -1` → 功放常通，**没有 GPIO 控制脚**
- `ES8311 id=83 at 0x18`（I2C 通）、`first i2s write: err=0 sent=1024 of 1024`（DMA 吃数据）
- **ROM 本身不产生任何声音**：flash 8 MB 里 `0x3040`–`0x3043` 零命中，irom 里 16 处全是产测
  与死代码，60 s trace DAC 写 0 次，IRQ0 handler 是空 `reti`，MAME 标 `MACHINE_NO_SOUND`。
  所以现在放的是**合成提示音**，不是仿真原机音效。

**ESP32-C3 的 I2S 时钟已证明不是问题**（查本机 IDF 5.5.3 源码确认）：C3 没有 APLL，
`I2S_LL_DEFAULT_CLK_FREQ` 就是 `PLL_F160M`；小数分频 `MCLK = SRC/(N + b/a)`，`a ≤ 511`，
而 `160e6 / 12.288e6 = 13 余 256000` → `N=13, b/a=1/48`，**零误差**。MCLK 走 GPIO 矩阵，
任意脚都能出，GPIO6 与能出声的 digimon-passport 板同脚。所以 48 kHz / 256×fs 这个组合
本身干净可用，别再往「时钟不对」上查。

**ES8311 的两个易错语义**：`0x31` 的 bit6 = `DSMMUTE`、bit5 = `DEMMUTE`，**写 1 才是静音**，
所以 `0x00` 是放行、正确；`0x06/0x07/0x08` 只在 ES8311 当 master 时起作用，
本板是 slave，写了也不生效，不可能是无声原因。

### 4.2 真正解决问题的改动（已编译、已烧写、已听音）

`firmware/digicore-c3/main/audio.c`，对照
`C:\Users\DuWeisi\digimon-passport\firmware\digimon-passport\managed_components\espressif__esp_codec_dev\device\es8311\es8311.c`
的 `es8311_init`（行 246-258）与 `es8311_start`（行 310-329）：

| 寄存器 | 改前（错） | 改后（官方运行值） |
|---|---|---|
| `0x0D` 系统电源 | `0xFC` | **`0x01`**（0xFC 只是过程值） |
| `0x17` ADC 参考 | 缺 | `0xBF` |
| `0x15` ADC ramp | 缺 | `0x40` |
| `0x45` DAC 输出路由 | 缺 | `0x00` |

**根因**：`0x0D` 停在系统电源寄存器的过程值 `0xFC`（模拟块断电），芯片处在
"I2C 读得到 ID、I2S 照收、DMA 照排空、喇叭一片安静"的状态 —— 正是用户报的症状。
这四个寄存器补齐后，同一份 I2S 数据立刻出声。

**一条被实机推翻的推断**（别再走回头路）：逐条核对官方驱动时曾判断「漏写 `0x10=0x1F` /
`0x11=0x7F`（模拟偏置 IBIAS）是唯一能解释无声的缺口，`0x44=0x08` 次之」。但 v1 这版
**并没有写这 5 条**，实机已经出声 —— IBIAS 的复位默认值在本板上够用，真正的缺口只有
`0x0D` 那一个。补 `0x10/0x11/0x44` 属于对齐官方的清理，不是修 bug 的必需项。

**上一轮那个"音量映射 bug"是假线索**：`audio_set_volume()` 在整个工程里**从未被调用过**
（grep 只命中 `audio.c` / `audio.h` 里的定义），`0x32` 一直停在 `es8311_init()` 末尾硬编码的
`0xBF` = 0 dB。所以把 `(100-pct)*255/100` 改成 `(100-pct)*0x40/100` 对声音**没有任何影响**，
响不响跟它无关。上一轮在这一点上判断错了。

顺带记下 `0x32` 的真实刻度（`es8311.c:145-156` 的 `vol_range`）：
`0x00` = −95.5 dB，`0xFF` = +32 dB，**每步 0.5 dB，`0xBF` 正好 0 dB**。原映射
`(100-pct)*255/100` 在 55 % 算出 `0x72` = −38.5 dB；而"修好后"的
`(100-pct)*0x40/100` 在 55 % 算出 `0x1C` = −81.5 dB，**方向是反的**。
真要接音量滑杆，正确写法是 `0xBF - (100-pct)` 这类浅调，或者干脆把 codec 钉在 0 dB、
音量走 `render_beep()` 的 16 bit 数字域（`amp = 12000 * s_volume_pct / 100`）。

- `0x31` 改成读-改-写 `& 0x9F`，而不是盲写 `0x00`
- `es8311_init()` 末尾回读 11 个寄存器打一行日志

**没烧过、没验证**，已从编译树移出。`0x44` 有风险：同款能出声的 digimon-passport 板走的是
`no_dac_ref=true`（写 `0x08`）而不是 `0x58`。现在这版已经出声，动它属于无收益风险，
除非将来要接麦克风或改善音质再捡。

## 5. 按键、设置菜单与自动熄屏

### 5.1 长按 A 等效 A+C（已完成）

`app_main.cpp` 里 `kAcHoldUs = 800000`（0.8 s 阈值，运行时可 `H <ms>` 改，`H 0` 关）。
检测块必须在 `update_buttons()` 里 `buttons_take_latched()` 之后、`if (s_inject_left > 0)` **之前**，
且判定必须用 `const int pressed = instant | (s_inject_left > 0 ? s_inject_mask : 0);`
—— 只读 `instant` 的话注入的按键永远触发不了长按（这个 bug 踩过）。

端到端证据（时钟界面）：

| 操作 | 结果 | 截图 |
|---|---|---|
| 6 次短按 A（`K 1 6`） | `10:52` → `11:52`（小时 +1） | `docs/shot_game.png` |
| `H 300` + `K 1 60`（按住 1 秒） | `11:52` → **`11:56`（分钟 +4）** | `docs/shot_chord3.png` |

日志：`long A (312 ms) -> A+C chord` → `press 05` → `port=ffd7`
（`0xFFD7 = 0xFFFF ^ 0x0028`，`0x28` = PORTA bit3(A) + bit5(C)）。

**代价**：任何界面长按 A 都会发和弦。不想要就 `H 0`。

### 5.2 实机熄屏时间是 16 秒（两条独立证据）

**文档**：[humulos DMC 用户手册](https://humulos.com/digimon/dmc/manual/) 原文
"If you don't interact with your Digimon for 16 seconds, the screen will turn off.
You can press any button to turn the screen back on."

**ROM 行为**：`ref/generalplus_gpce4_soc.cpp:170-194` 的 IO 映射里 `0x3036` 是 `System_Sleep`、
`0x300c/0x300d/0x300e` 是三个按键的 WakeUp_Mask。用 `emu/digicore.exe --seconds N` 逐档计时，
`0x3036` 的写入出现在 **17.2 s**（17.0 s 还没有、17.4 s 有）；扣掉开机动画稳定的 ~1.2 s，
正好 16 秒。

**关键陷阱**：ROM 写完 `System_Sleep` 后进入 `0x00537A` 的**紧密自跳循环，每秒重写该寄存器上千次**
（实测 20 s 内 `sleep_writes=4064`），而且这个循环**不响应按键**（`--press` 注入 A 后画面 sha 不变）。
所以**不能把"ROM 要求睡"当电平去灭背光**，那样会永久黑屏。模拟器改成自己计时，见 §5.4。

### 5.3 设置菜单（长按 B 1.5 s）

**样式来源**：`digimon-passport` 的菜单不是裸像素绘制，是 **LVGL 9 控件树**
（`main/digimon_app.c:2694-2756`），24 位 RGB888 交给 `lv_color_hex()`，字体用默认 Montserrat 14。
本节的所有几何都是把 LVGL 的 `lv_obj_set_pos` / `lv_obj_align` 换算成绝对坐标得到的，换算依据是
**LVGL 子对象坐标系是父对象 border + pad 之内**，所以卡片内的行要再叠加 `border 2 + pad 3`。

| 元素 | 参考板值 | 换算后绝对坐标 |
|---|---|---|
| 卡片 | `300 x 200` + `LV_ALIGN_CENTER` | `10..310 x 20..220` |
| 卡片底色 | `0xFBF9F0` 象牙白，不透明 90% | — |
| 卡片描边 | `0x2C3324` 深橄榄，宽 2 | — |
| 圆角 / 内边距 | 8 / 3 | — |
| 标题 `SETTINGS` | `TOP_MID, 0, -1` | y = 24，居中 |
| 行（5 条） | `278 x 24`，`(8, 36 + i*30)` | x 23..301，y = 61 / 91 / 121 / 151 / 181 |
| 行标签 | `LEFT_MID, +2` | 左沿 25 |
| 行值 | `RIGHT_MID, -2` | 右沿 299 |
| 版本号 | `TOP_RIGHT, -6, +1`，色 `0x5A6350` | y = 26，右沿 299 |

**三处照抄会抄错的细节**（都是参考板自己的实现，不是我的推断）：

- 主题色走 LVGL 的 `lv_color_to_u16`，那是截断而不是四舍五入，所以 `#2C3324` 是 **`0x2984`**、
  `#252C1F` 是 **`0x2163`**，不是按 `(c*size+127)//255` 算出来的 `0x29A4` / `0x2164`。
- 参考板想在选中行把文字压深（`MENU_INK`），但它自己的标签局部样式把行级色压过去了，
  `digimon_app.c:2471-2473` 的注释自认这一点。所以两态文字同色，别照着 `MENU_INK` 画。
- 一级菜单**没有帮助行、没有分隔线**（`digimon_app.c:2692-2766` 只建标题、5 行、版本号），
  版本号也不带 `v` 前缀。
| 选中条 | 整行 `0xFFD928` 黄，`bg_opa COVER` | 同行的 278x24 矩形 |
| 文字色 | 正文 `0x252C1F`，选中行 `0x17202A` | — |

**参考板自己有两处自相矛盾**（照代码而非注释实现）：`2202` 给选中行设了 `MENU_INK`，
但 `2471-2473` 的注释承认"行级文字色对标签无效"，实际选中行文字仍是 `0x252C1F`；版本号的注释写
bottom-right 而代码是 `LV_ALIGN_TOP_RIGHT`。本实现按**代码实际行为**取色，但保留了"选中行文字变色"
这个更好的视觉效果（用的是代码里就有的 `MENU_INK` 常量）。

**RGB565 换算**（`tmp/rgb565.py`，`(c * size + 127) // 255`）：

```
kPanelBg   #FBF9F0 -> 0xFFDD     kSelBar  #FFD928 -> 0xFEC5
kPanelEdge #2C3324 -> 0x29A4     kSelInk  #17202A -> 0x1905
kInk       #252C1F -> 0x2164     kMuted   #5A6350 -> 0x5B0A
```

**不能把 24 位字面量直接赋给 `uint16_t`** —— 编译器只报 `-Woverflow`，`0xFBF9F0` 会静默截断成 `0xF9F0`。

**文字**：项目没有字库，用 `main/font5x7.inc`（`tmp/make_font.py` 生成，ASCII 32..90 共 59 字符
× 5 B = 295 B），**放大 2 倍**画成 10x14、步进 12 —— 对应 Montserrat 14 的 16 px 行盒 / 10 px 大写高。

**5 个设置项**：

| 项 | 取值 | 默认 | 生效点 |
|---|---|---|---|
| `AUTO OFF` | `FOLLOW 16S / 30S / 60S / 2M / NEVER` | 16 | `update_sleep_backlight()` |
| `BRIGHT` | `20 / 40 / 60 / 80 / 100%` | 80 | `display_backlight_set()` |
| `VOLUME` | `0 / 20 / 40 / 60 / 80 / 100%` | 60 | `audio_set_volume()`，只在值变化时写 I2C |
| `AUTO SAVE` | `60S / 2M / 5M / OFF` | 60 | `maybe_snapshot_machine_state()` 周期 |
| `VERSION` | 只读，`v1.0.0` | — | 编译期 `DIGICORE_VERSION` |

持久化：NVS 命名空间 `digicore`，键 `auto` / `bright` / `vol` / `save`，只在值变化时写。

**`AUTO SAVE` 关闭的坑**：`period <= 0` 时要把 `s_snap_last_us` 顶到当前时间，否则下次打开会立刻触发一次。

**菜单不写 `fb[]`，直接推屏。** 这是踩出来的：guest 只重画自己动过的像素，写进 fb 的菜单文字在关闭后
不会消失（实测 `before 38699DC5 / menu open BA736F3D / after close BA736F3D`），而 DRAM 只剩 10 KB、
放不下 `128 x 112 x 2 = 28,672 B` 的备份。改成 `menu_present(uint8_t *strip, int w, int h, const MenuBackdrop *bg)` 全屏 1:1 渲染：
每行 `320 x 2 = 640 B`，`s_strip` 的 16,384 B 容 24 行，共 **10 个 band**，逐块
`display_draw_bitmap(0, y0, 320, 24, strip)`。副作用是**打开菜单也不会改动 `FB_CRC`**，硬判据全程稳定。

**卡片外面必须填游戏画面，不能填黑。** 第一版把卡片以外的像素统一写 `kPage = 0x0000`，设备上表现为
"菜单打开后游戏画面只剩一块黑、退出后也没完全恢复" —— 卡片 `10..309 x 20..219` 比 guest 窗口
`32..287 x 8..231` 更宽，`blit_frame()` 只推窗口，卡片左右各 22 px 的条带自己永远补不回来。
`MenuBackdrop` 就是为此存在：`app_main` 把 `fb[]` 指针、`stride=128`、窗口原点 `(0,8)`、窗口尺寸
`128x112`、屏上落点 `(32,8)`、`scale=2` 一次交代清楚，菜单用 `backdrop_px(x, y)` 反查游戏像素，
落在窗口外就返回黑（那里本来就没有内容）。菜单打开期间 guest 是停住的，所以采到的就是屏上当前那一帧。

**帮助行放在卡片外**的屏底黑边（y = 223），保持卡片本身像参考板一样干净——参考板一级菜单
没有帮助行、没有分隔线，也没有开合动画（`lv_anim` 全文 0 命中）。

**按键分发用边沿** `edge = latched & ~s_menu_pad_prev`，并在 `menu_open()` 后塞
`s_menu_pad_prev = instant | latched`；用电平会让注入的 B 连刷十几次。

**`menu_present()` 带 dirty 标志**，只在开菜单/按键后推，静置时零开销。

**布局预览**：`tmp/menu_preview.py` 用 Pillow 复刻 `render_line()` 的全部几何与配色，直接解析
`font5x7.inc`，输出 `tmp/menu_preview.png`（640x480）。改样式先看这张图，不用烧机。

### 5.3.1 按键阈值与 A+C 形态（2026-11-22 末）

| 手势 | 旧值 | 现值 | 依据 |
|---|---|---|---|
| 长按 B 开菜单 | 2000 ms | **1500 ms** | `digimon_app.c:337` `MENU_HOLD_US 1500000`；那份工程的 `PROGRESS.md:5047-5052` 记录了 3.0→1.8→1.5 的调参过程 |
| 长按 A 出 A+C | 800 ms | **1200 ms** | `digimon_app.c:356`；同族 ROM 实测 700 ms 不认、3200 ms 才认（`PROGRESS.md:3841-3862`） |

旧的两个数字没有任何实测或文档依据，纯手拍。

A+C 的**形态**也改了：原来是 6 帧（约 100 ms）脉冲且不释放 A，现在是**持续电平**——
长按到点后先放掉 A、按住 A+C，直到手指松开或 3.2 秒上限。参考板就是这么做的
（`digimon_app.c:3773` 先 `rom_key(4,0)` 放掉 A，`:3777` 再 `dg_set_button(5,1)`，
`:3789-3802` 等到有反应才松）。100 ms 的脉冲在这个 ROM 家族里几乎肯定是看不见的。

实测：
```
I (9637)  DIGICORE: port=fff7 (mv=2944)            ← A 按下
I (10845) DIGICORE: long A (1207 ms) -> A+C chord held
I (10845) DIGICORE: port=ffd7 (mv=2944)            ← A 释放 + C 按下
I (11720) DIGICORE: port=ffff (mv=2944)            ← 手指松开，全部释放
```

**菜单里长按 A 不再误关菜单**：之前长按 A 会注入 A+C，注入的 C 被菜单当成一次新按下，
于是菜单闪一下就关了。现在长按 A 和长按 B 都加了 `&& !menu_is_open()`。
**长按 B 到点也会先释放 guest 的 B**，否则这个 ROM 会把两秒的按住读成一串重复按键。

### 5.3.2 音量默认值与刷机复位

菜单默认音量 **20%**，而且**每刷一次固件都会回到 20%**：`menu_load()` 把当前二进制的
`__DATE__ " " __TIME__` 存在 NVS 的 `volbuild` 键里，与运行时读到的不一样就重置音量。
理由是刷了新镜像不该在别人手里突然炸响；背光、熄屏、自动存档不受影响。

顺带修掉一个开机顺序问题：`menu_load()` 现在在 `display_init()` **之前**跑，背光一上来就是
存着的亮度，不会先按编译期默认值亮一下再跳；`audio_init()` 之后、开机提示音**之前**补了
`audio_set_volume(menu_volume_pct())`，否则提示音永远用 `audio.c` 里写死的 55%。

### 5.4 自动熄屏与唤醒

`update_sleep_backlight()`（主循环里紧跟 `maybe_snapshot_machine_state()`）纯计时器：
`s_last_input_us` 记最后一次按键，`idle` 超过 `menu_auto_off_sec()` 就 `display_backlight_set(0)`。
**不跟随 ROM 的 `0x3036`**（原因见 §5.2）。任意键（含 `K` 注入）把 `s_last_input_us` 清零并重新点亮，
那一下按键**照常传给 guest**，不吞键。`display_backlight_set(80)` 的硬编码已改成 `s_brightness_pct`。

### 5.5 "实机已熄屏"提示

当模拟器熄屏设定 > 16 s，实机在 16 s 时已经黑了而模拟器还亮着，这个差异要标出来。
实现是往**屏顶 8 px 黑边**推一行 `MACHINE DARK`（`menu_banner_present()`，1:1 不缩放，
占 `s_strip` 的 320×8×2 = 5,120 B），停留 3 s。选黑边是因为它在 guest 窗口之外：
不覆盖任何游戏像素、不会被 guest 下一帧刷掉、也完全不碰 `fb[]`。
**这一项只验证到日志**（`machine would be dark now; banner at 16004 ms idle`），屏上是否可见需目视确认。

## 7. B 线（代码生成器重写）：三条路全试完，到此为止

- `AOT_LOCAL_MIN` 调阈值：**失败**（负结果第 10 条）

### 7.1 分组超块做了什么

`tools/aot.py` 里加了 `AOT_GROUP=1` 开关，**默认关，代码保留**，想复现直接加环境变量：

- `exit_targets(lines)` 从块尾提取字面量跳转目标，跳过含 ` return; }` 的逐指令提前出口
- `groupable(lines)` 排除 fallback / `term='sr'`（PC 高位运行期才知道）/ 计算跳转（CALL16、JMPF、JMPR）
- `build_groups(bodies)` 按 native 降序贪心；准入条件是 **`any(p not in gset and p != t for p in pred.get(t, ()))` 为假** -- 所有能静态命名的前驱都在组内，这就是「唯一入口」条件，靠它保住 `AotFn` 的单参数签名
- `groupify(members, loc)` 组内每块前插 `L_%06X:`，块尾 `aot_set_pc` 换成
  `r6 = (r6 & 0xffc0u) | 0xXXu; r7 = 0xYYYYu; goto LAB_%06X;`，共享桩统一做 `icount` 检查与
  `AOT_SAVE_REGS`；`icount` 用局部变量 `cyc` 累加，只在出口回写
- 表项：组首指向组函数，**组内非首块填 `nullptr`** -- 落到组中间的计算跳转掉解释器，行为正确只慢

### 7.3 为什么不行

1. **唯一入口条件把循环体全排除了。** 1466 块里只有 177 块满足「所有静态前驱在组内」，覆盖率
   12.1%；把上限放宽到 8 块 / 96 条只升到 12.5% -- **这是结构天花板，不是参数没调好**。
2. **省下的不如赔掉的多。** dispatch 次数确实降了 5.5%，但每次 dispatch 贵 0.8%、块体本身贵
   1.4%。组函数变大后 GCC 的 `-O3` 寄存器分配变差，Flash XIP 的代码局部性也变差。
3. **AOT 只占 40% 的 CPU，而且已经满帧。** `guest_fps` 贴着 57（游戏自身节拍上限），就算 AOT
   快 20%，端到端也只有 8%，还是看不出来。

### 7.4 顺带查出来的两个真 bug（已修，受益与 B 线无关）

**其一：周期计数器一直是死的。** `C3_SPLIT` 自 2026-11-19 起在 `main/CMakeLists.txt:33` 被写死
`-DC3_SPLIT=0`，那些计数器在设备上变成常量零（`unsp_glue.cpp:43-48` 的 `#else` 分支注释自己写着
"nothing ever increments them and the per-window percentages read 0"）。所以历史上所有
`caot/cpa/clk/cfn/daot` 打印出来的 0 **不是没负载，是根本没测**。

**其二：`aot_step()` 快路径漏计。** `unsp_glue.cpp:995` 的 `m_aot_blocks++` 之后直接 `return true`，
从来没累加 `g_disp_aot` / `g_cyc_aot`；只有慢路径 `:1689` 的 `if (hit_aot)` 做了。游戏运行时 100%
走快路径，所以就算打开 `C3_SPLIT` 也只会看到 `daot=0`。已补：

```cpp
m_aot_blocks++;
#if C3_SPLIT && defined(ESP_PLATFORM)
    SPLIT_ADD(g_cyc_aot);
    g_disp_aot++;
#endif
```

外加函数入口的 `SPLIT_T0()`。两处都留在代码里，`C3_SPLIT=0` 时编掉、零成本；以后要测性能把
`main/CMakeLists.txt:33` 的 `-DC3_SPLIT=0` 改成 `1` 重编即可（代价约 1.5% 帧时间，测完记得改回）。

### 7.5 真机实测的 AOT 开销构成（未分组的基线）

每块平均 **6.6 条 guest 指令**，`cpa=1289` 宿主周期拆开：

| 项 | 周期/次 | 占比 |
|---|---|---|
| 块体 `cfn` | 549 | 42.6% |
| 框架（LOAD_REGS/SAVE_REGS + 上下文同步 + 计数）| 699 | 54.2% |
| 查表 `clk` | 41 | 3.2% |

框架开销比块体本身还大 -- 这正是分组超块想砍的部分，也确实砍掉了一部分（`daot` -5.5%），
但块的颗粒度太小（6.6 条），省下的被组函数膨胀吃光了。

`recomp-bench` 的实测上限是 **1.98 宿主周期/条 guest 指令**（`HOT_BENCH cycles=26970559`
-> 134 周期 / 68 条）。当前实测 **1289 / 6.6 = 195 周期/条**，差两个数量级的真正原因是
**每块只有 6.6 条指令却有 1289 周期的固定开销**，不是单条指令翻译得不够好。

### 8.4 日志字段口径

`riram` / `rflash` / `rram` / `rpush` / `rdraw` / `rband` 是**该区间的 guest 指令数**（不是周期）。
`clk` / `cfn` = 每块查表 / 块执行周期；`gmax` / `smax` / `tmax` = 单帧 / 单次 `execute_run` /
单次 `tick` 的最大微秒数。`pd` / `pp` 是占**整个 1 秒窗口**的百分比（不是占那一帧）。

#### 8.2.1 采样陷阱：打开串口就会复位

pyserial 打开 `COM4` 时 DTR/RTS 的电平跳变会让 C3 复位。`tmp/send_cmd.py` 原本只等
0.3 s 就发命令，读到的是复位后约 0.8 s 的**半成品画面**（`FB_CRC 38699DC5`），
而稳定画面要**约 1.2 s** 才出现。曾经因此误判"硬判据失效"，差点去改本来没坏的代码。

- 已把 `send_cmd.py` 的等待改成 **2.5 s**，三次连测稳定返回 `62C4882E`
- 需要在同一上电周期内连续采样时，用 `tmp/poll_crc.py`（一次打开串口、内部多次发 `C`）
- 结论：`FB_CRC` 判据没有变，一直是 `62C4882E`；变的是采样时机

## 10. 硬件考证结论（供后续参考）

- SoC：**GeneralPlus GPCE4064B**，m'nSP 2.0，官方标称 **max 48 MHz**；MAME 用 96 MHz 是因为
  它的周期表是 1.2 与 2.0 公式的混合近似（MUL 计 12 周期 vs 官方 2）
- mask ROM：官网列 60 KB，但 dump 出来是 128 KB（0x4000–0x5FE5 非零）—— **冲突未解**
- SPI flash：**Macronix MX25L6433F 8 MB**
- LCD：**Sitronix ST7735V**，4-line SPI，RGB565 高字节先，96×96 可见区在 128×128 帧存内 y=18
- 按键：PORTA bit3/4/5 低有效（真机只有 3 个键）
- 供电：内置充电电池 + USB Type-C（不是 CR2032）

`ref/` 下有 MAME 的 gpce4 驱动源码、unSP 手册 PDF、以及 N64Recomp / vsemur / MooglyGuy-unsp
的 README（后三个是静态重编译的参考实现）。
