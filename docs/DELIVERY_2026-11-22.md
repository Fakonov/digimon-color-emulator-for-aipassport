## 1. 性能：大面积元素移动 100-120 ms → 42-70 ms

### 1.1 结论性数字

| 场景 | 改前 | 改后 |
|---|---|---|
| **大面积元素移动单帧**（切换时间画面 / 清理便便 / 出招动画） | **99–120 ms**（`rdraw` 83,569–245,020，HLE 关时实测） | **42–70 ms**（`rdraw` 19,637–39,585，同一手势 HLE 开）**2.2–2.8×** |
| 整屏重绘单帧 | 97 ms（`gmax=97,589`） | **54–58 ms**（同负载三次 54,316 / 57,879 / 57,846，±6% 是硬件抖动） |
| 连续按键风暴整秒 | 8.6 fps | **41–54 fps** |
| 绘制区 guest 指令（复杂帧） | 23–27 万条 | **1.9–4.0 万条（−84%）** |
| push 区 guest 指令/帧 | 112,797 | **2,335（−98%）** |
| push 区占宿主时间 | 5% 整秒窗口 | **0%** |
| 静止 fps / guest 占用 | 58.0 / 23–33% | 57.5 / 30%（单帧 `gmax=6,943`） |

那个 2.2–2.8× 是**同场景 A/B**：控制台 `X 0` / `X 1` 开关 `render_band` 的 HLE，
两种状态各发 5 次同样的 `K 1 2`（A 键两次），读每秒日志的 `gmax`：


### 1.2 第一刀：设备上跑的 AOT 块体从来没做过寄存器局部化

`tools/aot.py` 里 `AOT_LOOSE` / `AOT_LOCAL_MIN` 那套寄存器局部化早就写好了，
`tools/sync_c3_emu.py:151` 也确实设了 `env["AOT_LOOSE"]="1"`。但设备上那份
`firmware/digicore-c3/main/emu/aot_blocks.c`（3,906,743 B，mtime 12:22）里
`AOT_LOAD_REGS` 出现 **0 次** —— 它是一份未经局部化的旧产物。

按同一组环境变量重新生成（`tmp/aot_probe.c`，3,835,891 B，自报
`localised blocks : 985 (>= 4 insns)`），覆盖回设备目录后：
app bin 1,212,768 → **1,076,096 B（−11.3%）**，静态代码反而变小 —— 全量编译能看到
跨块的公共子表达式消除。

单看 60 块切片时局部化会让代码 +3.3%（块首 11 条 load + 块尾 11 条 store 对短块
不划算），全量却是 −11.3%。**别用切片判断全量效果。**

### 1.3 第二刀：`0x005B1E` 的 push 循环 HLE（整屏重绘最大的一笔）

census 数据（`tmp/census.log`，120 帧窗口）里 `BLK 005B29 9216` / `BLK 005B1E 9215`
—— 每像素执行一次，合计约 12.2 条指令 × 9,216 = 112,797 条 = **73% 的帧指令**。

从生成代码逐块读出它的真实语义：

```
0x005B1D  r4 = r2                  (count)
0x005B1E  r2 = r1 ror4             sh = ((r1<<4)|(sb&0xf))>>4; sb = sh&0xf; r2 = sh>>4
0x005B1F  r2 = r2 ror4             (对任何 sb，两次 ror4 结果恒为 r1>>8)
0x005B20  [3092] = r2              高字节先（spi2_txdata_w 只用 data&0xff）
0x005B22  [3092] = r1              低字节
0x005B24  nop
0x005B25  r2 = [3095] / test r2&0x0010 / jne 0x005B25   (bit4 恒 0，一轮通过)
0x005B29  r2 = [3094] ×2 / r4 -= 1 / jne 0x005B1E      (spi2_rxdata_r 恒 0)
```

**关键：循环体一次都不读内存，`r1` 从不被写，两次 `ror4` 恒等于 `r1>>8` ⇒ 每一轮
推出同一对字节 = 常量色填充，不是 blit。54 guest 周期/像素全是解释开销。**

`hle_fill_span()` 接管后：`rpush` **112,797 → 2,335（−98%）**，`pp` 5% → 0%，
`gmax` 76,438 → **52,030**。整屏重绘 97 → 52 ms。

**踩过的坑**：第一次钩 `0x005B1D`，`rpush` 完全没降 —— 因为 `0x005B1D` **不是块表
调用目标**（grep 在 `aot_blocks.c` 只有 `AOT_I` 一处，无 `set_pc`），它的指令是靠某块
fall-through 执行的。真正的 dispatch 入口是 `0x005B1E`。

### 1.4 第三刀：填色直达面板（有效但零收益）

`fill_run()`：在 `St7735` 里逐像素算 `store_pixel` 的同一索引公式、裁剪后写 `fb[]`，
省掉「`write16(0x3092)` → `Gpce4::write16` 的 switch → `spi2_txdata_w` 的 FIFO 记账
→ `St7735::data_w` 的拼字节」这一整串。`unsp_device` 通过 `m_lcd_fill` 函数指针接到
`Gpce4::lcd_fill_pixels`。

实测 `fillpx=9204` —— 每帧 9,204 个像素**全部**走快路径，`gmax=56,723` 仍在 54–58
区间。**结论：LCD 寄存器模型根本不慢**，原先「每像素 180 周期、一帧 30 ms」的归属
是猜错的。代码保留，但它不解决问题。

### 1.5 关掉 WiFi 全栈

`sdkconfig` 里 `ESP_WIFI_ENABLED` / `ESP32_WIFI_ENABLED` / `ESP_COEX_ENABLED` /
`ESP_WIFI_IRAM_OPT` / `ESP_WIFI_RX_IRAM_OPT` / `ESP_PHY_IRAM_OPT` 全改 not set
（原备份 `sdkconfig.bak-wifion`）。应用源码 grep `esp_wifi|esp_netif|lwip` 零命中 ——
这一整套全是 ESP-IDF 默认带进来的。app bin −46,480 B。

## 2. 游戏存档

### 2.1 游戏怎么存

8 MiB NOR 里两个 4 KiB 扇区 `0x7FD000`（主）/ `0x7FE000`（备），各一条 **92 字节**
记录（`0x00..0x5B`，其余全 FF）。游戏每 60.000 s 整扇区擦一次再整条重写，主备
**逐字节相同**（纯冗余双份，不是 A/B 轮换）。命令流实测
`SE → RDSR(05) → WREN(06) → PP(02)×92` ×2，无读回校验、无 WIP 轮询、无 0xD8
（擦除粒度就是 4 KiB）。一次存档只花 0.104 ms guest 时间。

**掉电容错游戏自带**：破坏主或备任一份（单 bit 翻转 / 整片 0x00 / 整片 0xFF /
局部擦除）都能从另一份恢复并重写一致。⇒ 固件不需要事务层，保证「任一时刻至少一个
槽 CRC 有效」即可，最坏丢最近 60 s，与真机一致。

### 2.2 固件侧

guest 的写落在 `SparseRom` 的 copy-on-write overlay（4 槽 × 4 KiB）里，掉电即失，
所以镜像到独立分区：

- `romstore.h` 新增 `overlay_export()` / `overlay_import()`；
- 新建 `saveimg.h` / `saveimg.cpp`：双槽 `kSlotStride = 0x10000`、`kHeaderSize = 24`
  （`#pragma pack` + `static_assert`），`SlotHeader = magic 'DGSV' + version + page_count
  + sequence + crc + page_no[2]`，`esp_rom_crc32_le` 覆盖 `page_no[] + 数据`；
  按 `s_next_seq & 1` 交替写槽；`saveimg_load()` 先读两个 header 选 seq 大的再读一个
  数据体（DRAM 只够一份）。
- `app_main.cpp`：`restore_save_image()` 在 `guest_init()` 的 `s_soc.reset()` 之后；
  `persist_save_image()` 在主循环 `blit_frame()` 之后 —— `overlay_writes()` 变化就记
  时间戳，静默 ≥1 s 后落盘。
- `partitions.csv` 改成 `roms 0x210000 0x280000` + `save, data, 0x41, 0x490000,
  0x020000`（128 KiB），表尾 0x4b0000。

### 2.4 为什么必须用注入验证

三次长跑（100 s 静置 / 200 s + 40 次按键 / 620 s + 200 次按键）**零 flash 写**。
一开始以为是模拟器丢了写命令，加 SPI 命令计数器后发现 `spise=0 spipp=0 spibyte=0`
—— 游戏压根没发过。再追下去发现 PC 轨迹在开机 17–18 秒后离开 flash 主循环
（`rflash` 归零），全时间耗在内部 ROM 的 `0x005251 / 0x005376` 上。

PC 环形缓冲（48 项，只记内部 ROM 入口）dump 出的完整一圈：

```
00537A 005376 00537A 005376 00537F 005390 005392 005398 0053A8 0053B0
005217 005240 005255 005251 005255 005251 005255 005251 00525A 00526B
00526D 0051BB 00526F 005898 005271 005289 005898 005322 005323 00532B
005365 00537A 005376 ...
```

逐段解码后：`0x00537F` 读 `[0x3000]`（PORT A 按键）与 `[0x0D06]` 比较，
`0x005365` 把当前按键写回 `[0x0D06]`/`[0x0853]` —— **这是轮询等在按键**，
不是冻屏。加日志字段 `pa=` / `d06=` 验证：空闲 `pa≈1,130`，注入 `K 1 2` 时掉到
`642–757`，之后 `rflash` 从 0 恢复到 80,052。⇒ **游戏在标题界面等输入，模拟器没坏。**

所以存档验证用注入：控制台 `W` 把 4,096 B 写进 overlay 页 `0x7FD`/`0x7FE`，
`persist_save_image()` 静默后落盘，复位读回比对。

## 3. 长按 A 等效 A+C

### 3.1 为什么需要

三键共用一条 ADC 电阻梯，一次只报一个触点 —— **真机的 A+C 和弦物理上做不出来**。
时钟编辑界面与死亡墓碑界面要这个和弦。

### 3.2 实现

`app_main.cpp:102` 后：`static int64_t s_ac_hold_us = 800000;`（运行时可被 `H <ms>`
改）。检测块在 `update_buttons()` 里 `int instant = buttons_state(); int latched =
buttons_take_latched();` **之后**、`if (s_inject_left > 0)` **之前**（放后面会晚一帧）：

```cpp
const int pressed = instant | (s_inject_left > 0 ? s_inject_mask : 0);
if ((pressed & BTN_KEY0) != 0) { ... esp_timer_get_time() 计时 ... }
```

用 `esp_timer_get_time()` 而不用帧数 —— 一帧 16.7–116 ms 不等，按帧计会飘。

**修掉的 bug**：原来读的是 `instant`（物理按键），而 `s_inject_mask` 要到后面才合并，
所以**注入的按键永远触发不了长按**。日志里 `press 01 -> holding` 持续 1,161 ms 却
没有 `long A` 就是它。

### 3.3 端到端验证

| 操作 | 时钟界面 |
|---|---|
| 6 次 `K 1 6`（短按 A） | `10:52 Set` → `11:52 Set`，小时 +1（`docs/shot_game.png`） |
| `H 300` + `K 1 60`（按住约 1 秒） | `11:52 Set` → `11:56 Set`，**分钟 +4**（`docs/shot_chord3.png`） |

```
I (16446) DIGICORE: press 01 -> holding
I (16446) DIGICORE: port=fff7 (mv=2944)
I (16759) DIGICORE: long A (312 ms) -> A+C chord
I (16759) DIGICORE: press 05 -> holding
I (16759) DIGICORE: port=ffd7 (mv=2944)      <- bit3 + bit5 同时拉低
```

`0xFFD7 = 0xFFFF ^ 0x0028`，`0x28` = PORTA bit3(A) + bit5(C)。**同一界面对短按与长按
给出两种不同行为，这是和弦被识别为和弦的证据。**

### 3.4 代价与开关

长按 A 在**任何**界面都会发和弦。不想这样的话 `H 0` 关掉，或把 `s_ac_hold_us` 改长。

## 4. 声音

### 4.1 更正：板上有 ES8311，不是压电片

`digimon-passport\firmware\ai-passport-tamago-main\components\bsp\include\bsp_pins.h`
是单一事实来源：I2C SDA=10 / SCL=7，**ES8311 codec @ 0x18**，I2S `I2S_NUM_0`
MCLK=6 / BCLK=5 / WS=3 / DOUT=2 / DIN=4，`BSP_I2S_PA_CTRL = -1`（功放常通）。

此前文档里「GPIO3 直推压电片」的说法是错的 —— GPIO3 是 I2S 的 WS 脚。
点名作废：`C3_PORT.md:160`、`EMU.md:72`、`HANDOFF.md:22`、
`_research/声音通路调研.md:16`。

### 4.2 这个卡带不产生任何音频数据（四条独立证据）

1. `roms/dmc_v1_base.bin`（8,388,608 B）里 `0x3040`–`0x3043`（DAC 寄存器）**0 命中**；
2. `roms/internal_rom_221017a.bin`（65,536 B）里 16 处，全是产测直通 `0x424A` 与
   四个**从未被调用**的淡出助手（`0x58D7`/`0x58F4`/`0x5911`/`0x592E`）—— flash→irom
   的 29 个 call 目标没有一个指向它们；
3. 60 秒动态 trace DAC 写 **0 次**；真机日志 `dac=0` 全程；
4. IRQ0 handler 是空 `reti`（`0x4834: DAA8 / 0B08 0001 / 90A8 / 9A98`），MAME 也标
   `MACHINE_NO_SOUND`。

硬件侧：GPCE4 是「两个 16-bit 软件通道 + 一个 14-bit DAC」，片上**无采样率寄存器、
无 DMA、无 FIFO**，guest 必须逐样本写 `0x3041`/`0x3042`。

### 4.3 做的是合成音，不是仿真

`audio.c` / `audio.h`：

- ES8311 最小寄存器序列（REG00 复位 → 时钟组 → 16 bit SDP → **REG0D = 0xFC** 同时
  拉起 DAC 与 ADC → REG14 = 0x1A → 解静音）；
- I2S std philips 16 bit stereo、48 kHz（96 MHz ÷ 2000 整除）、`auto_clear=true`；
- 按键音与开机音（880 Hz 70 ms + 1320 Hz 90 ms）由一个独立任务渲染，
  `audio_beep()` 只做非阻塞入队 —— 否则每次按下会给那一帧加 18 ms，正好毁掉帧时间。

**REG0D 的坑**：原先写 `0x01`，那是 system power 寄存器，`0x01` 只碰 ADC 侧，
DAC 根本没上电，于是 I2S 照收数据、DMA 照排空、喇叭一片安静。改成 `0xFC` 才会同时
拉起 DAC 与 ADC。

### 4.4 验证状态

```
I (606) audio: ES8311 id=83 at 0x18
I (608) audio: ready: ES8311 + I2S0 48000 Hz, amp always on
I (618) audio: first i2s write: err=0 sent=1024 of 1024
```

`0x83` 是 ES8311 的芯片 ID ⇒ I2C 通、寄存器写入执行、I2S DMA 真的吃下了 1024 字节。
**听感要人耳确认，我无法录音回传。**

## 5. 负结果清单（别重做）

| 做法 | 结果 | 原因 |
|---|---|---|
| MAME 式 `tick()` 定时器轮逐事件推进 → 按源合并 | `tmax` 30,174 µs → 607–10,771 µs（40×），但稳态 `guest_fps` 57.9 / `guest_pct` 30% **一位不动**，`tick_pct` 恒 0 | tick 不是稳态瓶颈。合并只消除首帧尖峰与抖动，代码保留但不指望它 |

## 6. 重绘帧的时间到底花在哪

一个重绘帧 ≈ **82,000 条 guest 指令**（`S → R → S` 差值：50 帧共 420 K 条，其中一帧
是重绘）。`rdraw`（`0x207900`–`0x207D40`）每秒约 38,346 条 —— 稳态几乎不跑，所以这个
数基本就是重绘帧的。

`pd` / `pp` 是**占整秒窗口**（96 M 周期）的百分比，`app_main.cpp` 里
`pct_draw = dcw * 100 / window_cyc`。所以 `pd=1` 意味着绘制区约 10 ms / 秒，
不是「绘制区不花时间」。

## 7. A1：把 `0x005F8B` 的乘加库从解释器里拿掉

### 7.1 语义（从 `aot_b005F8B` 逐条读出）

```
push r5                          ; 6 周期
r5 = r0 + 1                      ; r5 指向返回地址之后，即参数基址
r1 = [r5+3]                      ; 参数1 低字 (a_lo)
r2 = [r5+5]                      ; 参数2 低字 (b_lo)
MUL r1 * r2  -> r3 = lo, r4 = hi ; 无符号 16x16->32
r1 = r3 ; r2 = r4                ; r1 = 乘积低 16 位（返回值低位）
r3 = [r5+3] ; r4 = [r5+6]        ; a_lo, b_hi
MULS r3 * r4 -> r3 = lo, r4 = hi ; 有符号，带符号修正
r2 = r2 + r3                     ; 16 位加法，不传进位
r3 = [r5+4] ; r4 = [r5+5]        ; a_hi, b_lo
MULS r3 * r4 -> r3 = lo, r4 = hi
r2 = r2 + r3                     ; 16 位加法，不传进位
pop r5, r6, r7 ; ret
```

参数是两个 32 位值 `a = [bp+3]:[bp+4]`、`b = [bp+5]:[bp+6]`；返回 `r1` = 乘积低 16 位、
`r2` = 乘积高 16 位（即 **32×32→32，只取低 32 位**，忽略 `a_hi*b_hi`）。

### 7.2 参数布局用断点量出来，不是推的

纸上推了几版都对不上。最后在 PC 侧模拟器断点看：

```
emu/digicore.exe --frames 40 --press "0100:2:6" --bp 207A4C --bp-dump tmp/bp_a4c.bin
[bp] pc=207A4C r0/SP=0FAF r5/BP=0FB4
  [SP+0] @0FAF = 7A4C   <- 返回地址低字
  [SP+1] @0FB0 = 000C   <- 常数 12
  [SP+2] @0FB1 = 0000
  [SP+3] @0FB2 = idx
  [SP+4] @0FB3 = 0000
```

⇒ 参数就是 `12 × idx`，且 **`push` 是「先写后减」**（`aot_push_sr` =
`write16(sp,v); sp -= 1`，与 x86 相反）。

### 7.3 实现要点

只替换算术，**栈操作一行都不碰**：`push r5` 由 HLE 做，两处 `pop` 留给原代码，
所以栈始终平衡。收 94 周期 = 原始块 108 减去两处 pop 的 14。

`FB_CRC 62C4882E` 不变。**收益落在噪声里**（那 17 条 ALU 局部化后一整块只要约 150
宿主周期，2,157 次约 3 ms）。

## 8. 填色循环直达面板

见 §1.4。核心是把「逐像素走 LCD 寄存器模型」换成「逐像素直接写帧缓冲」。

```cpp
// St7735::fill_run(pixel, count)
for (uint32_t i = 0; i < count; i++) {
    // 与 store_pixel 同一索引公式
    const uint32_t idx = mv ? posx + posy * 0x200 : posy + (129 - posx) * 0x200;
    if (在窗口内) fb[ry * PANEL + rx] = pixel;
    推进 posx / posy（与 data_w 同样的回绕）
}
m_pixellatch = pixel; m_commandstep += count * 2;
```

`unsp_device` 通过 `m_lcd_fill` / `m_lcd_fill_opaque` 接到
`Gpce4::lcd_fill_pixels`，后者检查 `lcd.m_command == 0x2c`（RAMWR）才接管。

## 8b. 最后一刀（也是最有效的一刀）：`render_band` 的记录循环 HLE

### 8b.1 结构（从生成代码逐块读出来的，不是猜的）

```
0x2079FC  push r5 / sp -= 0x3D / bp = sp+1     prologue
0x207A18  call 0x203120                        ST7735 CASET/RASET
0x207A1F  call 0x005ACF                        发 LCD 命令
0x207A22  [bp+0] = mem[bp+0x40]                本行 y（y0 从参数区取）
0x207A2F  cmp  y, mem[bp+0x40]+mem[bp+0x41]    y < y0+h ?
0x207A31  goto 0x207D28                        否 → 函数出口
0x207A33  [bp+1] = 0                           记录索引清零
0x207A35  cmp  [bp+1], ds:[0x07B8]             记录索引 < 记录数 ?
0x207A3C  goto 0x207D15                        否 → 推这一行
0x207A3E  r5 = 0x0608                          记录表基址
   ...    单条记录：剔除 → 裁剪 → 填色或键控 blit
0x207D10  [bp+1]++ / goto 0x207A35
0x207D15  把 0x07BA 起 96 个像素经 0x005B41 推给面板
```

单条记录的算法（`tmp/draw_region_report.md` §5 已完整还原）：

- 剔除：`rec[8] != 1` / `rec[3] > y` / `rec[0x0A] < y` / `s16(rec[9]) < 0` /
  `s16(rec[2]) > 0x5f`；
- 裁剪三分支：左出血 `cnt = w - (-x0), srcskip = -x0, bias = 0`；右出血
  `cnt = 96 - x0, srcskip = 0, bias = x0`；否则 `cnt = w, srcskip = 0, bias = x0`；
  `cnt > 0x5f → 0x60`；
- `gfx == 0xFFFE` 走实心填充（写 `rec[1]`）；否则
  `src = (rec[7]<<16)|rec[6] + w*row`，`rec[0x0B] != 0` 时水平翻转
  （`src += w-1; src -= srcskip; src--`），色键 `0x07E0` 不写。

### 8b.2 接缝选在 `0x207A35`

钩在记录循环的**条件判断**处，不是逐记录也不是整个函数：

- 进入时 `[bp+1] < ds:[0x07B8]`：用 C 把这个行剩下的记录**一次处理完**，
  把 `[bp+1]` 写成记录数，然后 `set_pc(0x207A35)` 重入条件判断；
- 原代码发现 `[bp+1] >= 记录数`，自己跳 `0x207D15` 推屏。

这样 **`0x203120` 的窗口命令、`0x005B41` 的批量写、`0x207D28` 的出口全都不用碰**，
HLE 边界里只有纯 RAM 算术。单条记录按 520 guest 周期记账，并受 `m_icount` 预算限制
（预算不够就停在那里，下次 dispatch 接着来）。

### 8b.3 实测

见 §1.1 那张 A/B 表：`gmax` **99,468–119,753 → 42,323–70,681 µs**，`rdraw`
**83,569–245,020 → 19,637–39,585 条**。`FB_CRC 62C4882E` 不变 ⇒ 逐像素正确。

### 8b.4 还剩下的

`rband` 在 HLE 开时仍有 1.9–3.7 万条：每帧末尾 `icount` 不够再收一条记录（520 周期）
时退回 guest。要再往下压得把记账粒度降到像素级，但 42–70 ms 已经进到「一帧里能看清
动作」的区间，收益递减。

**翻转分支的处理（保守选择）**：`rec[0x0B] != 0` 走的水平镜像 blit 在这个卡带的任何
trace 里都**没有执行过**（census 里那几条块恒为 0）。从控制台用 `Q` 强制置位来验证
不成立——游戏每帧重写记录表，两次重绘之间状态不共享，实测三次 CRC 各不相同
（`FC01D21B` / `DA493962` / `9D8E628D`），测不出对错。所以 HLE 在进入记录循环前先扫
一遍翻转位：**任何一条记录带翻转，整行交回 guest**（`g_hle_band_flip` 计数）。代价是
这种行不加速，收益是已实测的 2.2–2.8× 不带任何未验证分支。

加上这段回退之后重跑了一次 A/B（`tmp/ab_band2.log`）：`X 0` 峰值
`gmax=118,958 / 100,478`、`rdraw=143,200 / 259,082`；`X 1` 峰值
`gmax=69,276 / 70,921 / 63,202 / 48,239`、`rdraw=19,920 / 19,351 / 19,596 / 39,532`。
⇒ 与回退前同一个量级，**翻转回退没有带来任何退化**（`FB_CRC 62C4882E` 也不变）。

## 9. 下一步（按性价比）

1. **B 线：全程序静态重编译**（把每条 guest 指令的固定成本再压一个数量级）。
   仓库里有证据说明上限：`recomp-bench` 在 C3 真机实测 **1.98 宿主周期/条**（直线块）
   到 **6.16**（循环块），当前 AOT 折算约 **20**（局部化后 `cfn=522` ÷ 11 条/块）。
   差距来源已量清：762 块 `.text` 656,880 B = 95.7 B RV32/条 guest 指令 ≈ 24 条 RV32
   干 1 条的活，`recomp/unsp_state.h` 的 `op_*` 全 `static inline` + 全局静态 `State`
   只要 4 条左右。三条必须复制的选择：状态放全局静态（8 KiB，不能上栈）／按 guest
   函数而不是基本块翻译（762 → 约 120 函数，尾调用在 `-O2` 链接期松弛成 2 字节
   `c.j`）／每块生成后与解释器逐位对拍。验收：`FB_CRC` 不变、块热点分布不变。
2. **把 `rband` 的残量也收掉**（记账粒度从整条记录降到像素级，或允许 HLE 透支一点
   预算在下一帧补扣）。
3. **给固件加 `SHOT` 协议**。现在验证画面靠 `C`（FB CRC）和 `L`（逐行 dump），
   `T` 命令能吐 128×112 完整帧（`tools/c3_shot.py` 解成 PNG），补一个兼容
   `passport-toolkit/bin/serial-shot.ps1` 的分条协议就能接进工具链。
4. **手测两件事**：时钟编辑界面与墓碑界面的长按 A（`H 300` 后按住 A 一秒），
   以及开机提示音是否听得见 —— 这两项要人耳人手。
