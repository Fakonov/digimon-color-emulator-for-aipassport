# 时间快进，且不动进化与进度：可行性研究

日期：2026-11-26
基线：`digicore-c3` v1.11.1（`firmware/digicore-c3/main/`）
范围：只做研究与方案设计。本文不含固件改动，也没有烧机。

---

## 0. 先把"快进"拆成两种，别混为一谈

| 语义 | 玩家看到 | 会不会推动进化 |
|---|---|---|
| **A. 倍速走时**（时间流速 ×N） | 时钟自己跑得飞快，昼夜交替 | **会**，一切"经过多少分钟"的逻辑同步加速 |
| **B. 跳时钟**（把时间拨到某个点） | 时钟瞬间跳到目标时刻 | **不会**，只改了显示与时刻判定 |

官方手册对 B 有一句原文（`docs/RESEARCH_DMC_MANUAL.md` §2）：

> Changing time will not speed up growth on Digimon.

这不是保护机制，而是 ROM 的数据结构决定的：成长挂在"分钟脉冲"上，不挂在"时钟数值"上。下面给出证据。

**本机的目标组合**：A 用于正常推进（进化、喂食冷却、昼夜都跟着走），B 用于"只想到某个时刻"（比如跳过夜晚）。两者都要，且都不能把存档搞坏。

## 1. ROM 里的证据链

### 1.1 唯一的计时器：`0x5BE2`（internal ROM）

`docs/RE_RTC.md` §1.3 已有完整反汇编，关键四行：

```
005C06: r4 = 0d03
005C0A: cmp r4, 00
005C0B: je 5c16                  ; 标志为 0 → 走 1 秒/次的常规路径
005C0D: r4 = 0cad                ; 标志非 0 → r4 = 秒
005C10: r4 += 3c                 ;      秒 += 60
```

也就是 `0x0D03 != 0` 时，每来一次"秒进位"就加 60 秒；60 秒必定溢出 → 进 1 分、置 `[0x0CB2] = 1`。

### 1.2 节拍从哪来：2 Hz 硬件中断

- IRQ7（internal ROM `0x486B`）：`[0x3054] & 1` → `[0x0CB1]++`，即每 0.5 s 一个半秒计数。
- `0x5BE2` 每次消费 `[0x0CB1] -= 2`，满两个半秒进 1 秒。
- 因此**正常模式：1 游戏秒 / 真实秒；`0x0D03=1`：1 游戏分钟 / 真实秒 = 60×**。

### 1.3 成长挂在哪：`0x209349` 分钟钩子

`0x209349` 是帧体 `0x230107` 每帧调用的钩子，开头就是：

```
209349: push bp
20934D: r4 = 0cb2
209350: cmp r4, 0
209351: je 209384          ; 没有"秒/分进位脉冲" → 直接返回
...
209352: call 00950F        ; 有没有宠物
209355: je ...
209356: call 0093BE        ; [0x0CE6]--
209358: call 0093D6        ; [0x0CE7]--
20935A: call 00946D
20935C: call 00948D
20935E: call 0094AD
```

而 `0x2093BE` 就是最朴素的一条：

```
2093BE: push bp
2093C1: call 0099CC
2093C3: cmp r4, 0
2093C4: je 2093C6          ; 条件不满足 → 不递减
2093C6: r4 = 0ce6
2093C9: r4 = [r4]
2093CA: cmp r4, 0
2093CB: je 2093D5
2093CC..2093D4: [0x0CE6] -= 1
```

**结论：`0x0CE6..0x0CE9` 是"分钟倒计时"，每来一个 `[0x0CB2]` 脉冲减 1。脉冲的数量由 tick 数决定，与 `0x0CAF/0x0CAE/0x0CAD` 的数值无关。**

这正是手册那句"改时间不会加速成长"的机制来源：B 方案只写三个字，不产生脉冲。

### 1.4 `0x0D03` 的其它引用（全镜像扫描）

`tools` 式扫描（`tmp/scan_refs.py`，按 `990C xxxx` 立即数模式匹配，不依赖线性反汇编）：

| 位置 | 动作 | 判断 |
|---|---|---|
| irom `0x005C07` | 读 | 上面说的倍速分支 |
| flash `0x201EA8` | 写 0 | 启动时清零一组 `0x0D00/02/03/04/05/06` |
| flash `0x2046A7` | 写 1，条件 `[0x081B] == 0x70` | ROM 自己的隐藏入口（**推测**：产线/演示模式） |
| flash `0x2046F0` | 写 0 | 另一处复位 |
| flash `0x20B4E2` | 读 | `[0x0CB3] != 0 && [0x0D03] != 0` → `[0x0CD4] = 1`，即把某个动画步进压到每帧一步 |
| flash `0x2302AA` | 写 0 | 主循环状态机的特定分支（`0x0C88` 不是 `5C/5E/5F` 时）才执行 |

所以 `0x0D03` 是一个"全局时间/演出加速"标志，读它的地方只有两处：时间进位、动画步进。**在育成/主画面状态下没有代码清它**（PC 侧实测 3600 帧后仍为 1，见 §2）。

### 1.5 与"进度"的关系

- 快照（`gueststate`）存的是整个 4 KiB RAM，`0x0D03` 是其中一个 word → 读档会把状态一起带回来。
- 游戏存档写 SPI flash（`0x7FE000`），`0x0D03` 不在里面，不影响存档格式。
- 进化、死亡、喂食冷却都是 RAM 里的计数器与状态机，随快照一起存，天然一致。

## 2. 本轮实测（PC，emu/digicore.exe）

命令（同一份出厂镜像，`--frames 900` = 15 guest 秒）：

```
.\emu\digicore.exe --clock-sync --frames 900 --press "8:150:170,20:300:320" --pc-hist tmp\hist_base.txt
.\emu\digicore.exe --clock-fast --frames 900 --press "8:150:170,20:300:320" --pc-hist tmp\hist_fast.txt
```

PC 直方图统计（`tmp/histcheck.py`）：

| PC | 含义 | base | fast |
|---|---|---|---|
| `0x5C17` | 常规秒进位 | **12** | 0 |
| `0x5C0D` | 快进分支（+60 秒） | 0 | **6** |
| `0x5BF3` | `[0x0CB1] > 1` 判定 | 789 | 316 |

RAM 快照（`tmp/base_14b.bin` / `tmp/fast_14.bin`）：

| 变量 | base | fast |
|---|---|---|
| `0x0CAF/0CAE/0CAD` | 0:03:06 | 0:06:00 |
| `0x0D03` | 0 | **1** |
| `0x0CB1` | 5 | 11 |

解释：

- fast 下 6 次进位 × 60 秒 = 360 秒 = 6 分钟，与 RAM 的 `0x0CAE = 6` 完全对上 → **快进确实走 ROM 自己的进位链，不是宿主伪造**。
- 名义 60×，这 14 秒只跑出 26×：PC 端没有 `set_sleep_inhibit`，ROM 用游戏内时间算 16 秒空闲，fast 下 0.27 真实秒就到，于是提前进入 sleep 路径，帧体调用从 940 次掉到 624 次，tick 被吞。
- 设备固件在 `app_main.cpp:2866` 已经 `set_sleep_inhibit(kGuestResumePc)` 拒绝这条路径，60 fps 稳定时应当是 1 脉冲/秒 → **接近 60×**。

> 未证实：设备端长时间 60 fps 下的实际倍率需要上机测（见 §6）。

## 3. 为什么现在不能直接在设备上置 `0x0D03 = 1`

四个坑，按严重程度排：

### 坑 1（致命）：`clock_sync()` 每 250 ms 把时钟纠回锚点

`app_main.cpp:2449`。它算 `dev = 墙钟 - guest`，超出 ±2 s 就 `guest_clock_write()` 覆盖 `0x0CAF/0CAE/0CAD`，并把 `[0x0CB1]` 清零、`[0x0CB2]` 置 1。

快进时 guest 每 250 ms 前进 15 分钟，`dev` 恒定 −900 s → 每 250 ms 写回一次。后果：

- 时钟在"真实时间"和"真实时间 + 15 分钟"之间来回跳，屏幕破相；
- 依赖时刻的判定（睡觉、闹钟、每日事件）反复触发；
- `[0x0CB1] = 0` 白丢半个 tick，倍率不可控。

成长计数器的脉冲反而还在（每次写回都置 `0x0CB2`），所以**进化不会停**，但会出现"时钟乱跳 + 倍率失控"，不能交付。

### 坑 2：自动存档持久化的是旧锚点

`app_main.cpp:2201` 在快照成功后 `wallclock_persist()`。快进 1 小时真实时间等于 60 游戏小时，锚点却没动 → 断电重开后时间倒退，读档也会把旧时间写回快照。

### 坑 3：快照里带着 `0x0D03`

在快进状态下存档，之后关掉开关再读档，RAM 里的 `0x0D03 = 1` 会回来，快进"复活"。

### 坑 4：没有入口

菜单 7 项里没有开关；控制台也没有命令。

## 4. 三个方案

### 方案 A：ROM 倍速（`0x0D03`）—— 推荐做主线

**做法**：菜单加 `TIME LAPSE`，`OFF / 60X`；开=写 1，关=写 0。

**进化/进度的安全性**：走 ROM 原生进位链，脉冲数与倒计时严格 1:1，规则、顺序、判定全不变，只是时间轴整体压缩。

**必须同时改**：
1. `clock_sync()` 在快进时不再纠偏，改成"锚点跟随 guest"（新增 `wallclock_track_local()`，只更新锚点、不写 NVS）。
2. 关快进时 `wallclock_adopt_local(guest_clock_sec())`，让锚点继承虚拟时间，时钟不回跳。
3. 快照前先 adopt 再 `wallclock_persist()`。
4. 读档/复位后按菜单值重写 `0x0D03`，压过快照里的旧值。

**代价**：倍率固定 60×，不能再调（`+0x3C` 硬编码在 internal ROM `0x5C10`，改不了）。

### 方案 B：跳时钟（`wallclock_set` + `guest_clock_write`）—— 配套做

**做法**：菜单加 `CLOCK +1H`（或控制台 `t <epoch>`，已有）。

**效果**：RTC 立刻 +1 小时，**成长计数器一个都不减**。跨过睡觉时间会立刻触发睡眠/起床，这是 ROM 自己的时刻判定，属于预期。

**用途**：只想跳过夜晚、或想比 60× 更快到达某个时刻时，用 B 叠加 A。

### 方案 C：宿主注入 tick（可调倍率）—— 不做

`0x5BE2` 每帧只消费一组 tick（`[0x0CB1] -= 2`），要一帧推多分钟只能反复调用 ROM 函数，需要手工构造栈帧；收益（可调倍率）不如"B 跳时钟 + A 跑一段"直接。留作以后需要 300× 以上时的备选。

## 5. 落地方案（方案 A + B）

### 5.1 `wallclock.h/.cpp`

新增：

```cpp
// 快进时把锚点跟到 guest 的虚拟时间：只更新锚点，不落 NVS。
// 下一次 wallclock_persist()（自动存档）才写盘。
void wallclock_track_local(int64_t local_sec);
```

实现与 `wallclock_adopt_local()` 相同，去掉 `wallclock_persist()`，`s_source = "lapse"`。

### 5.2 `menu.h`

```cpp
enum { MENU_ITEMS = 8 };
enum {
    MENU_IDX_CHORD = 0, MENU_IDX_CHORD_AB = 1, MENU_IDX_LAPSE = 2,
    MENU_IDX_AUTO_OFF = 3, MENU_IDX_BRIGHT = 4, MENU_IDX_VOLUME = 5,
    MENU_IDX_AUTOSAVE = 6, MENU_IDX_ABOUT = 7,
};
int menu_time_lapse();      // 0 = OFF, 1 = 60X
```

索引一变，`s_sel` 的默认值与 NVS 里的老值都要跟着改（`menu.cpp:65` 的 `s_sel = MENU_IDX_AUTO_OFF`）。

### 5.3 `menu.cpp`

- `kLapseNames[] = {"OFF", "60X"}`，`s_lapse_idx`，`press_b()` 里 `case MENU_IDX_LAPSE` 轮换并 `save_u8("lapse", ...)`。
- `value_text()` / `name_for()` 各加一行 `TIME LAPSE`。
- `menu_load()` 读 `lapse`。

### 5.4 `app_main.cpp`

```cpp
static bool s_time_lapse = false;

static void apply_time_lapse()      // 菜单/读档/控制台共用
{
    s_time_lapse = menu_time_lapse() != 0;
    s_soc.ram[0x0D03] = s_time_lapse ? 1u : 0u;
    ESP_LOGI(TAG, "time lapse %s (0x0D03=%u)", s_time_lapse ? "60x" : "off",
             unsigned(s_soc.ram[0x0D03]));
}
```

`clock_sync()` 开头插：

```cpp
if (s_time_lapse) {
    const int64_t g = guest_clock_sec();
    wallclock_track_local(g);       // 锚点跟着虚拟时间
    s_clock_check_us = esp_timer_get_time();
    return;                         // 不纠偏
}
```

关闭快进的路径（菜单 B 键 / 控制台）：

```cpp
wallclock_adopt_local(guest_clock_sec());   // 继承虚拟时间，不回跳
apply_time_lapse();
clock_sync(true);
```

`snapshot_machine_state()` 在 `wallclock_persist()` 之前：

```cpp
if (s_time_lapse) wallclock_adopt_local(guest_clock_sec());
```

恢复（`gueststate_load` 成功之后）与冷启动种子成功之后各调一次 `apply_time_lapse()`，压掉快照里的 `0x0D03`。

控制台加 `f <0|1>`（或 `lapse <0|1>`），并在 `CLK` 行加 `lapse=` 字段，方便台架验证。

### 5.5 可选：只在"游戏画面"生效

`0x0C88` 是界面状态（主界面 `0x1C/0x1D`、设置 `0x02`）。可以只在主界面打开 `0x0D03`，进设置/时钟编辑时临时清 0，避免快进把玩家正在操作的界面推走。**推测**：ROM 的时间编辑界面每帧清 `0x0CB0` 的行为（v1.11.1 已记录）与 `0x0D03` 无关，但值得上机确认。

## 6. 验证计划

### PC（已有能力）

1. `--clock-fast` vs `--clock-sync`，同一 `--frames` 下比 `--pc-hist` 里 `0x5C0D`/`0x5C17` 的次数，期望 fast 的 `0x5C0D` ≈ 秒数 ÷ 1、base 的 `0x5C17` ≈ 秒数。
2. `--ram-dump` 比 `0x0CE6..0x0CE9`：需要先进育成画面（本轮四种 press 序列都停在设时钟/主界面，**未完成**；`docs/EMU.md` §验证 5 的序列在本 build 上不能复现，需要重新标定按键）。
3. 快进 + 存档来回：`--load-flash` / `--save-flash` 对比 `0x7FE000` 的 8 字节写法是否仍一致。

### 设备（COM4）

1. 烧 `f 1` 后读 `CLK` 行：`guest` 每分钟小时数应当推进；跑 60 s 真实时间，期望 `0x0CAE` 增加约 60。
2. 关掉快进，确认时钟停在虚拟时间上继续走 1×，不回跳。
3. 快进 10 分钟 → 自动存档 → 硬复位：`clock seeded ... from nvs` 应当是虚拟时间，不是旧时间。
4. 快进状态下存档 → 关快进 → 读档：确认 `0x0D03` 回来后是 0。
5. 长跑 30 分钟（真实），看是否有 `STUCK`/panic；快进让动画加速，CPU 负载会上升，注意 `guest_fps`。

## 7. 风险与边界

- **快进会把死亡条件一起加速**：手册的 6 小时连续受伤、12 小时饥饿都会按 60× 到来。快进前先手动确认一次状态，或者只在"蛋/成长期"用。
- **跨天**：ROM 的 RTC 只有时分秒，没有日期；`0x0836/0x0837` 是另一套分钟计数（本轮实测 base 里是 29684/29716，fast 里是 FFFF，语义未定，**推测**是"当日分钟 + 累计分钟"）。快进跨天时昼夜与"每日"逻辑会连续触发，属于正常。
- **倍率不是精确 60×**：受 tick 丢失影响；快进的目的是"省时间"，不是"精确计时"。
- **不要用快进替代对时**：快进结束后锚点已经是虚拟时间，想回到真实时间用 `t <epoch>`。

---

## 8. 结论

1. **ROM 自带正确答案**：`0x0D03 = 1` 就是 60× 时间倍速，走的是它自己的进位链，成长/进化/死亡与时钟严格同源，不存在"只改显示"的问题。
2. **"改时间不加速成长"是另一条路**：只写 RTC 三字，不产生分钟脉冲，成长不动。两条路都保留。
3. **设备端缺的不是 ROM 能力，是宿主配合**：`clock_sync` 的 250 ms 纠偏、锚点持久化、快照里的旧标志，这三处不改，直接置位只会得到"时钟乱跳 + 倍率失控"。
4. 改动集中在 4 个文件、约 80 行；不需要改分区表、AOT 块、显示或音频路径。

## 9. 落地实现（v1.12.0，已烧 COM4）

按 §5 实现，并按用户要求补了长驻提示与一键取消。

### 9.1 档位与算法

`app_main.cpp` 的 `kLapseModes[]`：三档都打开 ROM 的 60× 进位标志，倍率只由**注入周期**决定（一次进位 = 1 游戏分钟）：

| 档 | 注入周期 | 进位/秒 | 标称 |
|---|---|---|---|
| OFF | — | 0 | 1×（ROM 自己的时钟，不动） |
| 15X | 4.000 s | 0.25 | 15 游戏秒 / 真实秒 |
| 60X | 1.000 s | 1 | 60 游戏秒 / 真实秒 |
| 300X | 0.200 s | 5 | 300 游戏秒 / 真实秒 |

三条关键实现细节，都是被真机数据逼出来的：

1. **不能依赖 ROM 自己的 2 Hz 进位。** 这个卡带大部分时间 `int off`，中断落不进去；实测"只开 `0x0D03`、不注入"的 60X 只有 5.9×（十秒才进一次分钟）。所以三档全部由宿主注入。
2. **不注入的帧要把 `[0x0CB1]` 清零**（`time_lapse_step()` 的 else 分支）。否则 ROM 自己的半秒 tick 会额外送一次进位，同一档实测在 5.9× 和 51× 之间乱跳。
3. **累加器按时钟走，不按帧走**；触发后减周期而不是清零，避免丢余数。倍率因此与帧率解耦。

### 9.2 宿主配合

- `clock_sync()` 新增 `s_lapse_x > 1 && !force` 分支：只 `wallclock_track_local()` 跟随，不纠偏、不清 `[0x0CB1]`。
- 关闭倍速时 `wallclock_adopt_local(guest_clock_sec())` 把虚拟时间收为新锚点，时钟不回跳。
- 快照前（`snapshot_machine_state()`）先 adopt 再 `wallclock_persist()`，断电后从虚拟时间继续。
- 恢复（`restore_machine_state()` / `U`）后 `sync_time_lapse(true)`，压掉记录里的旧 `0x0D03`。
- `sync_time_lapse()` 每帧维持标志位：ROM 的 `0x2302A8` 分支会清 `0x0D03`，不重写会让快进几秒后自己停。
- 新增 `LAPSE` 台架日志行（每 5 s，仅快进时）：`LAPSE 300x 5664ms ticks=25 guest=22:00:09 scr=0000`，用于在设备内部测量，避开串口往返延迟。

### 9.3 提示条（模态，单行，窗口下缘）

三次迭代：顶部 8 px 边条（被 30 px 圆角遮罩裁掉一半）→ 正中 280×84（挡住宠物）→ **窗口下缘单行 240×22**。

- 位置 `y = 240 - 22 - 2 = 216`：游戏窗口是 `y 24..215`，所以整条落在窗口外面，宠物和下排状态图标都不挡。
- 一行字：`LAPSE 300X  B=STOP`（2× 5×7 字体，深字象牙底，2 px 深橄榄边框）。
- 只推 22 行 × 240 px，比窗口 blit（192×192）小一个数量级，因此**每帧重画**即可，不再限频。
- 弹出时机：①在设置卡里切完倍速、按 C 关卡的瞬间；②控制台 `f 0..3` 直接开启且菜单没开时。
- 关闭时 `bezel_paint()` 重画外壳再补一次全窗 blit。

### 9.4 按键取消

**短按 B**。提示条激活期间是模态的：`update_buttons()` 一进来就只认 B 的按下沿（物理按键或 `K` 注入都算），A/C 全部吞掉、pad 保持释放、长 A 也开不出菜单。

```cpp
if (s_lapse_toast) {
    const int edge = buttons_take_latched();
    const bool b_tap = (edge & BTN_KEY1) != 0 ||
                       (s_inject_left > 0 && (s_inject_mask & BTN_KEY1) != 0);
    if (b_tap) { s_lapse_toast = false; menu_set_time_lapse_idx(0); sync_time_lapse(true); ... }
    ... return;   // everything else is swallowed
}
```

菜单里仍保留 `TIME LAPSE` 行（按 B 循环四档），NVS 记忆，重启后保持。

控制台：`f` 打印当前档，`f 0..3` 直接切；`CLK` 行新增 `lapse=..x ticks=..`。

### 9.5 真机实测（COM4，v1.12.0）

测量在固件内部完成（`LAPSE` 行自带毫秒时间戳与 guest 时刻），避开串口往返延迟——控制台 `S` 的回复在 300× 下晚到一秒就是 300% 误差。每档 10 秒窗口：

| 档 | 实测 guest 增量 | 实测倍率 | **实际 10 分钟 → 游戏时间** |
|---|---|---|---|
| 15X | 120 s / 10.1 s | **11.9×** | **约 119 分钟（2.0 小时）** |
| 60X | 540 s / 10.0 s | **53.7×** | **约 537 分钟（9.0 小时）** |
| 300X | 1500 s / 5.0 s | **300×** | **约 3000 分钟（50 小时）** |

- 15X 偏低约 20%：它的注入周期是 4 s，而每帧最多注入一次，采样窗口里的帧率抖动会吃掉一两次进位。
- 60X 偏低约 10%：注入 10 次只被 `0x5BE2` 消费 9 次（游戏在标题与主界面之间切换，个别帧不跑帧体）。
- 300X 与标称一致（5 秒推进 25 分钟）。三档都随游戏状态小幅浮动，这是 ROM 帧体执行率决定的，不是定时器。

```
I (6027)  DIGICORE: LAPSE 300x 5664ms  ticks=25 guest=22:00:09 scr=0000
I (11044) DIGICORE: LAPSE 300x 10680ms ticks=50 guest=22:25:09 scr=0000
```

其余已验证：开启弹提示条、菜单里改档关卡后弹条、B 键停、锚点采纳虚拟时间、重启读回 NVS 档位。

未测：真机 60 fps 满速、有存档有宠物时的倍率（当前设备无存档，游戏停在标题/主界面之间，帧体执行率不稳定）；断电/读档一致性；卡片像素需人眼确认（串口只证明推送成功）。
